## 0. 分析框架

把问题拆成三层，避免混着讨论：

| 层 | 问题 | 说明 |
|---|---|---|
| ① 世界会怎么变 | 外界发生了什么 | 配对删了、信号断了、系统睡了…… |
| ② local-mic 凭什么知道 | **发现机制** | 事件 / 轮询 / 操作失败被动暴露 / 用户手动 |
| ③ 知道了该怎么做 | **反应** | 重连 / 报错码 / 提示用户 / 什么都不做 |

**用户纠正的关键前提**：local-mic 有两种运行态，需求完全不同。

| 运行态 | 职责 | 需要设备列表吗 |
|---|---|---|
| **后台静默**（托盘常驻，无窗口，绝大多数时间） | 保住链路、保证 PTT 随时可用 | ❌ 不需要 |
| **UI 打开**（主窗口，用户主动看/选） | 展示状态、让用户选设备 | ✅ 需要，**且按需取即可** |

⇒ 「新配对的设备」只在 UI 打开时才有意义；后台静默时监听它是**无的放矢**。

## 3. 三个结论

**① 用户的两点判断都成立**

- 「删除配对要处理」——✅ 但缺的主要是**语义**（应报 `pairing_required`，现在是 `connecting`），
  以及「删了没断链」的残余情形（A2）。
- 「新配对不需要后台监听」——✅ **完全成立**。列表是实时读注册表的，UI 打开即最新；
  后台监听新配对设备是纯粹的浪费。

**② 「信号弱断连」其实已经有机制** —— 走 `ConnectionStatusChanged` ⇒ `disconnected` ⇒ 重连。
真正的洞不是它，而是它的反面：**B9 假连接**（系统说连着，实际不通 ⇒ `Tick` 直接 return，永不自愈）。
这是**唯一一个现有架构完全无解**的场景。

**③ 所有待定方案的共同前提，是同一个未知**：

> **「世界已经变了，但 `IsConnected` 仍返回 true」会不会发生？在哪些场景下发生？**

- 若 B5（关蓝牙）/ B6（休眠唤醒）/ B2（遥控器休眠）**都会**触发断链事件 ⇒
  假连接罕见 ⇒ 只需修 A1 语义 + A2 残余，watcher 价值有限。
- 若其中任何一个**不触发**（尤其 B5、B6）⇒ 必须上一条**健康度探测**，
  而这同一条探测**顺带解决 B9**。⇒ 一次投入，两个收益。

**🔬 ③ 的实测回答（23:15 补）**：三个场景**全部会触发断链事件**，无一例外。

| 场景 | `IsConnected` 是否谎报 | 证据 |
|---|---|---|
| B5 关蓝牙 | ❌ 不谎报，**同一秒** `disconnected` | X1，3 次复现 |
| B6 睡眠唤醒 | ❌ 不谎报，resume 即 `disconnected` | X2 |
| B2 遥控器休眠 | ❌ 不适用——**根本没断**（34 min 零断链） | X3 |

⇒ 落到「只需修 A1 语义 + A2 残余」这一支，**不必上健康度探测**，watcher 价值进一步下降。

**🔬 计划外挖出的头号结论：断连后必须「按键唤醒」（三轮独立验证）**

初稿的场景表里**没有这一项**——它不在 ① 层（世界怎么变），而在 ③ 层（知道了该怎么做）：
断连本身能被正确感知，但**恢复不了**。

| 轮次 | 触发方式 | 干等 | 结果 | 按键后 |
|---|---|---|---|---|
| X7 | 关蓝牙 2 min | 3 分 44 秒（22 轮） | ❌ 全败 | ✅ 5 s 内连上 |
| X8 | 关蓝牙 2 min | 5 分 04 秒（30 轮） | ❌ 全败 | ✅ 1 s 内连上 |
| X2 | 系统睡眠 | 3 分 36 秒（22 轮） | ❌ 全败 | ✅ 秒连 |

对照组：断连仅 **35 秒**（未达休眠阈值）时，开蓝牙后 **6 秒自愈**（X1 第三次）。

⇒ **修法优先级因此被推翻**：原判第一优先的"修 `ConnectAsync` 干等不触发连接"**降级**
（设备休眠时主动踢也没用），升为第一优先的是**断连时提示"请按一下遥控器"**。
⚠ **休眠阈值未量化**（只知道在 35 s ~ 2 min 之间）⇒ **不得写进代码**，
文案只能说"若长时间连不上"，不能写"等 X 秒后按键"。
⚠ 该提示须**条件触发、不能常驻**（静置实测不掉线 ⇒ 99% 的时间它都是噪音）。

## 4.5 🎁 活样本：A1 场景此刻正在发生（21:08 取证）

实验还没开始，就撞上了 **A1（配对被删）的真实态** —— 遥控器此刻**不在配对列表里**
（`probe_ble.py list` 只剩 A955 BT / LT75PRO-BT1 / RAPOO BT3.0 MS，无 RC003），
而 local-mic 的接缝自报是：

```
STATE = connecting      detail = 连接 C0:5D:39:F8:50:C7
ERROR = pairing_required  retryable = False   msg = 等待连接超时（10 秒）
DEVICE model=RC003  paired=false  battery=84
```

**这就是用户说的「界面没有任何反应」的实锤**：

| 事实 | 证据 |
|---|---|
| 后端**知道**配对丢了 | `error.code = pairing_required` 已正确产生（`BleRemote.cs:324`） |
| 但**界面看不出来** | `MainForm` 只显示 `state` + `detail`，**不显示 `error.code`**（全仓库无 `LastError` 引用） ⇒ 状态行是「状态：连接中 · 等待连接超时（10 秒）」 |
| `retryable=false` 却仍在无限重试 | 语义自相矛盾：告诉客户端"别等了"，自己却每 5 秒重连 |
| `battery=84` 是**陈旧值** | 协议 §8.1 规定非 `connected` 时电量不可信，但 UI 照常显示 84% |

⇒ **A1 真正的缺口不是"发现不了"，是"发现了但不告诉用户"。**
这比加 watcher 便宜得多，且不动协议（`pairing_required` 已在 `error.code` 开放值域内）。

### 顺带：重新配对 = 免费回答 A5/A6

用户接下来必然要重新配对遥控器，观测脚本正好开着 ⇒ 顺带拿到两个答案：

- **A5**：新配对一台（当前设备已丢）时，local-mic 会不会**自动接管**？多久？
- **A6**：重配后蓝牙地址是否还是 `C0:5D:39:F8:50:C7`？
- **#32 复核**：重配后首次连接是否复现 `枚举特征失败：AccessDenied`？

### 重新配对全过程时间线（21:09–21:12，观测脚本实拍）

```
21:09:23  STATE=connecting   ERROR=pairing_required(retryable=false)  DEVICE paired=false battery=84
21:09:31  STATE=error        等待连接超时（10 秒）
21:09:31  STATE=connecting              ← 每 10 秒一轮，横跳 20 次
   ...     （error ↔ connecting 循环，共约 3.4 分钟）
21:12:47  STATE=connected    已连接      ← 用户在设置里添加设备后自动连上
21:12:47  DEVICE model=RC003 paired=False battery=84
21:12:55  DEVICE battery=85             ← 电量在更新，链路真活
```

| 待答问题 | 结论 |
|---|---|
| **A5 新配对会否自动接管** | ✅ **会**。用户只在 Windows 设置里添加设备，**没开 local-mic UI**，程序在下一个重连周期自动连上（T+204 s，即失败循环的第 20 轮命中） |
| **A6 重配后地址是否变** | ✅ **不变**，仍是 `C0:5D:39:F8:50:C7` ⇒ 重配不会让已存配置失效 |
| **#32 首次连接 AccessDenied** | 本次**未复现**，一次即 `connected` |

#### 🔴 两个新发现（都不是原计划要找的）

**发现 1：`paired=False` 却已连接、能读电量。**
`connected` 之后 `device.paired` 仍是 **False**（电量 84→85 说明链路真活）。
⇒ **`IsPaired` 现在三个方向都不可信**：已配对报 False（本次）、删除后仍报 True（#32）、
刚配对报 False（本次）。协议 §8.1 让客户端"据 `state` 判断电量可信"是对的，
但**若插件哪天改用 `paired` 做门控就会误判** —— 建议写进协议或插件手册的注意事项。

**发现 2：重连失败循环在 `error` ↔ `connecting` 之间每 10 秒横跳，与协议 §8.1.1 的意图冲突。**
协议原文：「典型：重连定时器每 5 秒重试失败一次**不得**重复广播……若每次重连失败都刷一轮
`connecting` + `error`，客户端即便想安静，也被迫每 5 秒响应一次」。
现状是每轮产生 `error`(失败) → `connecting`(下次尝试) 两条，取值**交替**故不违反字面规则
（"同一取值不得重复"），但**完全违反该条的意图**：客户端（dsh 插件）会被迫每 10 秒响应一轮。
⇒ 稳态设计应是：重试期间**停在一个稳定取值**（如 `disconnected` 或 `error`），
不要每次尝试都切回 `connecting`。**待决策**（属协议语义问题，可能要动 `docs/PROTOCOL.md` §8.1.1 的措辞）。

### 🔴 代码级发现：`ConnectAsync` 只是"干等"，从不主动触发连接

`BleRemote.cs:118-139` 的流程：

```csharp
dev = await BluetoothLEDevice.FromBluetoothAddressAsync(address);
if (dev.ConnectionStatus != Connected) {
    挂上 ConnectionStatusChanged 处理器;
    await Task.WhenAny(事件, Task.Delay(10000));      // 干等 10 秒
    if (超时) return ConnFail("等待连接超时（10 秒）");  // ← 直接返回，没走下一步
}
var svcResult = await dev.GetGattServicesAsync(...);   // ← 只有"已连接"时才走到这
```

**`FromBluetoothAddressAsync` 本身不发起连接**；在 WinRT 上真正触发底层连接的是
`GetGattServicesAsync()` 这类 GATT 操作。而现在的代码**超时后就直接返回了**，
根本没走到 `GetGattServicesAsync` ⇒ **每一轮重试都只是"问一句连上了吗"，从来没有"踢一脚"**。

⇒ 那 3.4 分钟**不是 local-mic 重试出来的**，而是 Windows 自己（已配对设备收到广播后自动回连）
在某个时刻建立的；local-mic 只是在事后"发现"它连上了。

**这也解释了为什么 Python 探针能连、local-mic 却要等**：bleak 的 `BleakClient.connect()`
内部会调 `GetGattServicesAsync` 做服务发现 ⇒ **主动触发了连接**。
⇒ 函数头那句注释「已配对设备即使不广播也能连上，FromBluetoothAddressAsync 不需要广播，
已由 Python 版探针在真机上验证」**推错了对象**：探针能连是因为它发了 GATT 请求，
不能证明"干等"也能连。

> ⭐ **这条根因不依赖上面的时长数据**：它来自**读代码**（`ConnectAsync` 超时后直接返回，
> 永远不执行 `GetGattServicesAsync`），与"恢复用了几分钟"无关。时长只是旁证。
> 即便恢复时间随机波动，只要"从未主动触发"成立，结论就成立。

**待验实验 X6（对照 + 重复，吸取"两点不能当规律"的教训）**

设计原则：**不测单点时长，做同一次断连事件内的对照，并重复 ≥2 次**。

| 步骤 | 操作 | 记录 |
|---|---|---|
| 1 | 关蓝牙 ⇒ 等 `disconnected` ⇒ 开蓝牙 | 时间点 |
| 2 | **立刻**（不等 3 分钟）用 bleak **主动** `connect()` | 主动连接耗时 T_主动 |
| 3 | bleak 立刻断开，观察 local-mic 自己多久接上 | 干等耗时 T_干等 |
| 4 | 重复步骤 1–3 至少 2 次 | 看两组耗时是否有数量级差异（不是看单点） |

- 若 T_主动 **秒级**、T_干等 **分钟级**，且两次重复都如此 ⇒ 证实"主动触发有效"。
- 风险：bleak 会占住唯一的 GATT 客户端（一个设备同时只允许一个），
  故步骤 3 必须立刻断开，并观察 local-mic 是否因此被卡住（这也是要记录的现象）。
