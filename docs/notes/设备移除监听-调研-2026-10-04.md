# 调研：用 DeviceWatcher 监听「遥控器配对被删除」（2026-10-04）

> 过程稿，只增不改。结论若与手册冲突，以手册为准。
> 起因：用户在「设置 → 蓝牙」里删掉遥控器后，**local-mic 界面毫无反应**（界面僵在"已连接"的假连接态）。
> 方案选型时用户选了 **事件驱动（B 方案）**，并质疑"噪音不一定有那么多"⇒ 本调研用真机实测回答。

---

## 0. 结论速览

| 问题 | 实测结论 |
|---|---|
| net48 + `Microsoft.Windows.SDK.Contracts` 能不能用 `DeviceWatcher`？ | ✅ 能。一次性探针 0 error 编译通过并跑通（SDK 在 `~/.workbuddy/binaries/dotnet-sdk`，NuGet 缓存已有包） |
| 静默期噪音有多大？ | **常态几乎为零**：90 秒观察 = 4 条 ADDED（启动时枚举）+ 2 条枚举完成，**0 条 UPDATED / 0 条 REMOVED**。但**偶发会来一阵**：另一次 30 秒观察里连吐几十条 `UPDATED`，内容是 `System.ItemNameDisplay` 在 **`MI RC` ↔ `小米蓝牙语音遥控器`** 之间来回跳 |
| 噪音怎么免疫？ | 按**属性白名单**过滤：只认配对相关属性，忽略 `System.ItemNameDisplay` / `System.Devices.Icon` / `System.Devices.GlyphIcon` |
| watcher 事件里的 `Pairing.IsPaired` 可信吗？ | ❌ **不可信**。两个 watcher 都把这台明明已配对的遥控器报成 **`paired=False`**（同期 local-mic 报已配对、能连上、能读电量）⇒ 判据**不能**用事件里的 `IsPaired` |
| 那还能拿什么判据？ | 靠 **AQS 过滤本身**：配对态选择器 `GetDeviceSelectorFromPairingState(true)` 由系统按 `System.Devices.Aep.IsPaired:=True` 过滤 ⇒ 设备一旦不再匹配就发 **Removed**。"在不在结果集里"是可靠事实，"事件里的 IsPaired 字段"不是 |
| **删配对是否真的触发 Removed？** | ✅ **已验证（真机）**：设置里点「删除设备」后 **<1 秒**就收到 `REMOVED`（探针启动后 4.59 s 命中） |
| 用哪个选择器？ | 🔴 **必须用配对态选择器**，**不能**用单地址选择器 —— 删配对时单地址 watcher **一条 REMOVED 都没发**（它的 AQS 只按地址匹配，与配对状态无关），只有配对态 watcher 发了 |

## 1. 两个候选选择器（实测 AQS 原文）

```
配对态全部设备：
System.Devices.DevObjectType:=5
  AND System.Devices.Aep.ProtocolId:="{BB7BB05E-5972-42B5-94FC-76EAA7084D49}"
  AND (System.Devices.Aep.IsPaired:=System.StructuredQueryType.Boolean#True
       OR System.Devices.Aep.Bluetooth.IssueInquiry:=System.StructuredQueryType.Boolean#False)

只盯这一台（按地址）：
System.Devices.DevObjectType:=5
  AND System.Devices.Aep.ProtocolId:="{BB7BB05E-5972-42B5-94FC-76EAA7084D49}"
  AND (System.DeviceInterface.Bluetooth.DeviceAddress:="c05d39f850c7"
       OR System.Devices.Aep.Bluetooth.IssueInquiry:=System.StructuredQueryType.Boolean#True)
```

| 选择器 | 启动时 ADDED 数 | 说明 |
|---|---|---|
| `GetDeviceSelectorFromPairingState(true)` | **3**（遥控器 + A955 BT + LT75PRO-BT1） | 已配对 BLE 设备全集；⚠ 注意里面**混进了 `IssueInquiry:=False` 的兜底条件**，含义是"或未完成查询"，实测没造成额外噪音 |
| `GetDeviceSelectorFromBluetoothAddress(addr)` | **1**（只有遥控器） | 最精准，噪音面最小 |

⇒ **推荐用「配对态选择器」**（因为要靠它判定"已配对"这个条件本身），再用**地址**过滤只关心这一台。

## 2. 三次观察的原始数据

探针：`%TEMP%\watcher-probe`（**未进仓库**，一次性），两个 watcher 同时跑，每条事件打相对时间戳。

| # | 时长 | ADDED | REMOVED | UPDATED | 枚举完成 | 备注 |
|---|---|---|---|---|---|---|
| 1 | 30 s | 配对态 ≥1（出现在 35.76 s） | 0 | **数十条** | 2 | `UPDATED` 全是 `System.ItemNameDisplay` 在 `MI RC` ↔ `小米蓝牙语音遥控器` 之间抖动（27.6–33.4 s 集中爆发） |
| 2 | 30 s | 配对态 3（0.01 s）+ 单地址 1 | 0 | **1 条**（`ItemNameDisplay` + `Icon` + `GlyphIcon`） | 2 | 基本安静 |
| 3 | 90 s | 配对态 3 + 单地址 1 | 0 | **0 条** | 2 | 完全安静 |

**判读**：噪音**不是**"枚举风暴"那种持续噪音，而是**偶发的设备显示名抖动**（设备广播名被 Windows 反复重新解析，可能在遥控器状态切换时出现）。
⇒ 用户"噪音不一定有那么多"的质疑**基本成立**：常态下几乎为零；但**必须**加属性白名单，否则那阵抖动会穿透到 UI。

**副产品发现**（值得单独记住）：`DeviceInformation.Pairing.IsPaired` 在 watcher 事件里报 `False`，而设备其实已配对。
这与 PITFALLS #32 里"删除配对后 `IsPaired` 可能仍返回 true"是**同一条 API 的两个方向的不可靠** ⇒
**结论：任何"配对状态"判定都不要读 `Pairing.IsPaired`**，要么读注册表（`DeviceFinder` 已有实现），要么看 watcher 的 Added/Removed。

## 3. 真要落地时的建议实现（尚未开发，等 §4 的结论）

1. `DeviceInformation.CreateWatcher(BluetoothLEDevice.GetDeviceSelectorFromPairingState(true))`
2. 事件处理只认两种：**`Removed`**（按设备 id 匹配我们选中的地址 ⇒ 判定配对被删）+ **`Added`**（重新出现 ⇒ 清错误、可重连）
3. `Updated` **先看属性白名单**：只处理 `System.Devices.Aep.IsPaired`；`ItemNameDisplay` / `Icon` / `GlyphIcon` **直接丢弃**
4. 去抖：Removed 后延迟约 2 s 再确认一次（防那阵抖动误伤），确认没了才 `Disconnect()` + `SetError("pairing_required")`
5. 生命周期：与 `_timer`/`EnsureConnectedAsync` 串行化（PITFALLS #10：连接必须串行化），别在 `Removed` 里直接抢着连

## 4. 决定性实验（已做，2026-10-04 20:42）

用户批准「直接拿遥控器试」⇒ 探针 `wait` 模式跑起来后，在设置里删除遥控器，抓到：

```
  0.05s  [配对态] ADDED    小米蓝牙语音遥控器  paired=False
  0.05s  [单地址] ADDED    小米蓝牙语音遥控器  paired=False
  4.59s  [配对态] REMOVED  id=BluetoothLE#…c0:5d:39:f8:50:…   ← 删除后 <1 秒命中
  4.73s  [探针]   已捕获
  5.42s  [单地址] UPDATED  System.ItemNameDisplay=MI RC         ← 之后单地址 watcher
  …（持续到 14.72 s，上百条 MI RC ↔ 小米蓝牙语音遥控器 抖动）
```

**三条硬结论**：

1. ✅ **删除配对确实触发 `REMOVED`，延迟 <1 秒** ⇒ B 方案成立。
2. 🔴 **只有「配对态选择器」会发 REMOVED**；「单地址选择器」全程一条 REMOVED 都没有。
   ⇒ 实现必须用 `GetDeviceSelectorFromPairingState(true)`，再用地址/id 过滤出我们那台。
3. 🔴 **删配对后那阵 `UPDATED` 噪音会集中爆发**（5.4–14.7 s 上百条，全是 `System.ItemNameDisplay`
   在 `MI RC` ↔ `小米蓝牙语音遥控器` 之间抖）⇒ **属性白名单不是可选项，是必需品**；
   同时解释 §2 第 1 轮那阵抖动：设备处于"刚删/刚配"这类状态切换期就会抖。

## 4.1 顺带修正：local-mic 不是"完全没反应"

删掉配对后读接缝，local-mic **确实动了**，但**慢且语义错**：

```
{"op":"state","state":"connecting","detail":"连接 C0:5D:39:F8:50:C7"}
{"op":"device","id":"C0:5D:39:F8:50:C7","model":"RC003","paired":false,"battery":84}
```

| 现象 | 解释 |
|---|---|
| 它感知到了 | 删除配对**通常会真的断链** ⇒ `ConnectionStatusChanged` 触发 ⇒ Tick 里重连 |
| 但显示的是「连接中」而不是「配对被删」 | 失败被归成"连接不上"，进入**无限重试**循环，**不会提示用户去重配** |
| 反应有延迟 | 依赖链路断开 + 下次 Tick（有客户端 5 s，无客户端 30 s；实测这次约十几秒） |
| **真正的死角** | 删除配对但**链路没断**时（不是必然断），`Tick` 的 `if (_ble.IsConnected) return;` 直接跳过 ⇒ **彻底无感**，界面永远停在"已连接" |

⇒ 所以这个修复的价值不在"从 0 到 1 的感知"，而在**把延迟从十几秒压到 <1 秒，并把语义从"连接中，等着重连"改成"配对已丢失，请重新配对"**。
