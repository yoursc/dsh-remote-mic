## 零、先回答你的核心问题：哪些路被验证过

你手里的硬件（RC003）要连上 Windows，**只有一条路是真正被验证通的**：

```
遥控器 ──BLE(ATVV协议)──► PC 端自己实现 ATVV 解码 ──► 虚拟声卡/直接打字 ──► 输入框
```

**为什么必须自己在 PC 端实现 ATVV？**

ATVV 是 Google 为 Android TV 定义的自定义 GATT profile。**Android 原生支持，Windows 从来没有实现过。**

有一份非常硬的论证（来自 `QYHHHH/BleRemoteBrideg` 的可行性评估文档）：

> 证据：Windows 上所有可用方案（`MiVoiceMic`、`techdou/VoiceHub`、`QL-4/RemoteMapper`）**都是自己在 PC 端实现 ATVV 解码 + VB-CABLE 虚拟声卡**。若 Windows 原生支持，这些项目一个都不需要存在。

所以这条路不存在"偷懒走系统 API"的可能。要么你自己解码，要么不用。

同时这也意味着：**这是一条已经被至少 5 个独立项目走通、并且互相印证的路**。你不需要重新探索方向，只需要把它重写一遍、按自己的需求裁剪。

## 二、ATVV 协议规格（可直接写代码）

这份规格是从 `getsayall/remote-mic-app-windows` 的 `crates/sayall-core/src/atvv.rs`（完整实现 + 单元测试），与 `mi-input` 的实测结论交叉验证出来的。**协议逆向这部分，你完全不用自己做。**

### 2.1 GATT UUID（Google ATVV 标准 base）

Base UUID：`AB5E0000-5A21-4F05-BC7D-AF01F617B664`

| 角色 | UUID |
|---|---|
| Service | `AB5E0001-5A21-4F05-BC7D-AF01F617B664` |
| TRANSMIT（主机 → 设备，写命令） | `AB5E0002-5A21-4F05-BC7D-AF01F617B664` |
| AUDIO（设备 → 主机，通知音频帧） | `AB5E0003-5A21-4F05-BC7D-AF01F617B664` |
| CONTROL（设备 → 主机，通知控制事件） | `AB5E0004-5A21-4F05-BC7D-AF01F617B664` |

### 2.2 主机 → 设备（写到 TRANSMIT）

| 命令 | 字节序列 | 备注 |
|---|---|---|
| GetCapabilities v1.0 | `0A 01 00 00 03 03` | 握手第一步 |
| MicrophoneOpen（version ≥ 0x0100） | `0C 00` | 新版固件不带 codec |
| MicrophoneOpen（旧版） | `0C 00 <codec>` | |
| MicrophoneClose（version ≥ 0x0100） | `0D <session_id>` | |
| MicrophoneClose（旧版） | `0D` | |
| MicrophoneExtend（version ≥ 0x0100） | `0E <session_id>` | 续期用，防止超时掐断 |
| MicrophoneExtend（旧版） | 不支持 | |

### 2.3 设备 → 主机（CONTROL 通知，首字节 = opcode）

| opcode | 事件 | 载荷 |
|---|---|---|
| `0x0B` | Capabilities | 见下文解析 |
| `0x08` | MicrophoneOpenRequested | — |
| `0x04` | StreamStarted | `[1]=interaction, [2]=codec, [3]=session_id` |
| `0x00` | StreamStopped | — |
| `0x0A` | DecoderSync | `[4..6]=predictor(i16 BE), [6]=step_index` |
| 其他 | Unknown | 按 opcode 记录、忽略 |

> `DecoderSync` 很关键：`predictor` 和 `step_index` 是 ADPCM 解码器的初始状态。**收到它必须重置解码器状态**，否则每次会话开头都会有一小段爆音。

### 2.4 Capabilities 解析规则

```
version  = u16 BE @ [1..3]
if version >= 0x0100:
    codecs      = [3]
    interaction = [4]
else:
    codecs      = [4]        # 旧版布局
    interaction = 0

# RC003 固件有个怪癖：version 报 0x0100 但 codecs 为 0，
# 此时 codec 信息藏在 [4] 的低两位
if version >= 0x0100 and codecs == 0 and len >= 9 and ([4] & 0x03) != 0:
    codecs      = [4]
    interaction = 0x03

selected_codec = 0x02 if (codecs & 0x02) else 0x01
sample_rate    = 16000 if selected_codec == 0x02 else 8000
frame_size     = u16 BE @ [5..7]，若为 0 则回落默认 120
```

**判断设备可用与否**：`sample_rate == 16000`（即 codecs & 0x02 成立）。SayAll 的 `AtvvCapabilities` 里专门有个方法就是判这个——**16k 才算支持 MicControl 级音频，8k 的直接拒掉。**

### 2.5 音频数据

| 参数 | 值 |
|---|---|
| 采样率 | 16 kHz |
| 声道 | 单声道 |
| 编码 | **IMA ADPCM，4 bit** |
| 帧大小 | **120 字节/帧**（可通过 caps 覆盖） |
| nibble 顺序 | **高 4 bit 先解码** |
| 解码状态 | **帧间连续**（每帧结束时保留 predictor / step_index，作为下一帧初始状态） |

**每帧时长换算（RC003 / RC001 实测，已校正）**：

```
120 字节 = 240 个 4-bit 样本 = 240 samples ÷ 16 kHz = 15 ms
```

正主仓库的 A/B 实测完美吻合这个公式：RC001 按住 16.57 s 到达 1105 帧，1105 × 15 ms = 16.575 s，**分毫不差**。

**这个公式是你验证链路质量最有用的工具**——录音结束后拿「到达帧数 × 15 ms」除以「实际按住时长」，直接得到**实时送达率**。实现时仍按 caps.frame_size 走，别硬编码 120。

### 2.6 状态机与容错

必须处理的三件实事：

1. **MTU 必须协商到 247**
   这是硬前提，不是优化项。默认 MTU 23 时每包 20 B，15 ms 连接间隔下只有 **~1,333 B/s**，而 IMA ADPCM 空口需要 **8,000 B/s**——**差 6 倍**。协商到 247 后有 ~16,267 B/s 才够用。
   如果你的实现出现"声音断续、像卡碟"，第一件事查 MTU。

2. **RC003 固件会跳过 mic_open_request 直接 stream_start**
   实测观察到的行为：某些固件不发 `0x08`（MicrophoneOpenRequested），直接发 `0x04`（StreamStarted）。**状态机不能把 0x08 当作必需的中间状态**，否则会卡死。

3. **Stop 事件可能重复，必须去重**
   不去重会导致"乒乓"——反复开关会话，日志刷屏、音频错乱。用一个 `session_id` + 当前状态联合判断。

4. **⚠️ 固件免费音频窗口只有约 5.7 秒（前面写的 60 秒是错的，已更正）**

   这是 RC003 上最容易被误判成"音质差"的坑。正主仓库的真机取证：两次长按（12.95 s + 8.32 s = 21.3 s）只解出 11.43 s，**两次都精确地在约 5.7 秒处被掐断**——因为固件只给了这么长的免费音频窗口，超时就被切断。

   解法是**主动续期**，节拍写死：

   | 项 | 值 |
   |---|---|
   | 续期命令 | `0x0E <session_id>`（MicrophoneExtend） |
   | 发送间隔 | **2.5 秒** |
   | 排期时机 | `StreamStarted`（0x04）到达时排定 |
   | 取消时机 | `StreamStopped`（0x00）到达时取消 |
   | 兼容处理 | 协议版本 < 0x0100 编码失败 → 不再排期 |

   实测验证：修复后 RC003 长按 17.55 s 不再掐断，GATT 日志记录到 7 条 `T 0E 57` 每 ~2.5 s 一次。**对 RC001 无副作用**（6 条 `T 0E 1A` 续期，会话与文字均正常）。

   > 为什么这个坑在 RC001 时代没暴露：RC001 用户习惯短按 1–3 秒，从不触窗。而你要用嘴说 prompt，一句话轻松超过 5.7 秒——**所以这个坑对你来说是必然踩到的，不是偶发**。

### 2.6.1 RC003-MS 专属：开箱第一件事是「删掉配对，重新配对」

这是 RC003 用户的头号报障，而且**不是应用缺陷，是配对态问题**：

| 状态 | 实测数据 |
|---|---|
| **初次配对（有病）** | 按住 17.55 s → 只到达 638 帧 → 音频 9.57 s，**实时送达率 55%**；表现为 ~300 ms 爆发（约 20 帧）+ 150–250 ms 间隙，共 53 段 |
| **重配对后（正常）** | 按住 12.83 s → 到达 844 帧 → **98.7%**（短会话 95.8%）；1 次间隙；文字输出全对 |
| RC001 基准 | 100% |

**根因**：初次配对时协商出的 BLE 连接参数带宽不足，固件按实时速率生成音频帧但空口只送得出约 55%，其余**在源头就丢了**——应用层无法恢复，重解码也没用。

**处置（按序试）**：

1. 删除 RC003 配对后重新配对（重新协商连接参数）← **99% 的情况这一步就好**
2. 遥控器充电（低电量可能触发固件降功耗节流）
3. 缩短与主机的距离、避开干扰

**怎么量化验证**：用上面那个公式，`到达帧数 × 15 ms ÷ 按住时长`。正主仓库留了个现成做法值得抄：加个环境变量 `SAYALL_GATT_LOG=<文件>` 的诊断日志（默认关闭），记录每条 GATT 通知（A=音频 / C=控制）与应用写入（T=发出），含墙钟毫秒、长度、前 24 字节。**建议你的 MVP 第一天就把它做进去**，它是后面所有链路问题排查的基础设施。

> ⚠️ 顺带一个 Windows 专属坑：**一个设备同时只能有一个 GATT 客户端**。正主写的旁路侦听探针 `gatt_snoop.rs` 在主应用持连接时被挡（`FromIdAsync` 返回 code-0 错误）。所以**调试时不要同时开两个程序连同一个遥控器**，诊断要靠应用内日志，不能靠第二个进程旁路抓包。

### 2.7 Windows 上怎么找到这个 GATT 服务（不依赖 WinRT 的做法）

mi-input 记录了一个很实用的技巧，纯 ctypes 就能做：

> **每个 BLE GATT 服务在 Windows 上以"服务 UUID 作为接口类 GUID"暴露设备接口。**
> `SetupDi` 枚举该 GUID → `CreateFile` → `BluetoothGATT*` API（`BluetoothApis.dll`）

这条路径的好处：**不需要 Rust、不需要 WinRT、不需要 .NET**，Python ctypes 就能完成全套 BLE 交互。对你想快速验证、想让 AI 帮你快速迭代的场景，这是最低门槛的入口。

（另一条识别路：用标准 GATT Model Number 特征 `0x2A24` 识别 RC001 / RC003。mi-input 给出 USB 侧 VID=2717 PID=32B8。）

### 3.1 归因修正（RC003 真机取证，比"驱动层丢弃"精确得多）

`mi-input` 当年只能观察到"收不到"，归因为"驱动层丢弃"。正主仓库 2026-09-23 用提权探针把因果链**完整闭合了**：

```
设备确实上报（HidP_GetButtonCaps 取证：0x80/0x81/0xF1 确实在报告里）
        ↓  报告到达 WUDFHost.exe（提权只读实测，30 次命中：三键各 3 次）
        ↓
Windows 事件层零事件（Raw Input 采集对照）
        ⇒ 丢弃发生在 HID→VK 键码映射阶段（kbdhid）
```

**根因不是"设备不上报"，而是 Windows 的 HID→VK 映射表里根本没有 `0x80` / `0x81` / `0xF1` 这三个 usage。**

### 3.2 免提权的路：四条通道全部实测 failed

别再自己试一遍了，正主已经穷尽过：

| 通道 | 结果 |
|---|---|
| 用户态 `CreateFile(GENERIC_READ)` 直读 TLC | `err=5`（拒绝访问）；阳性对照 8/17 设备可打开且均为 Shared 模式 |
| 厂商 GATT 服务 `8A7A0001` 的 3 个通知特征 | 可订阅但**零通知**（同窗口电池特征有通知，证明回调链路是通的） |
| GATT HID 服务 `0x1812` 特征枚举 | **全部 AccessDenied**，`0x2A4B` 报告描述符拿不到 |
| Raw Input 注册 5 种组合（含厂商页 `0xFF00`） | 三键**零事件**；同采集内确定键 `VK_RETURN`×2、主页键 `VK_HOME`×1 按次数精确到达（自证对照） |

想绕过映射去读原始报告，会被 RIM（Raw Input Manager）的独占打开挡住。

### 3.3 有解，但代价是提权（正主已 7/7 PASS）

唯一走通的路：**注入 `WUDFHost.exe`**。关键在于 RC003 的 HID 设备由**用户态**驱动宿主承载（`Service=mshidumdf`、`LowerFilters=WUDFRd`、`WUDF\DriverList=HidOverGatt`），报告的生产端在 RIM **之前**。

| 项 | 值 |
|---|---|
| 拦截点 | `DeviceIoControl`，`IOCTL 0x80018483`，`in_len=8` / `out_len=9` |
| 报告结构 | `report_id(0x01)` + `modifiers` + `reserved` + **3 × uint16 usage（小端）** |
| 输入报告长度 | 121 字节，3 个 LinkCollection，4 个 ButtonCaps |
| 改写时机 | **必须在 `onEnter`**（实测 30 次命中中 `onLeave` 输出变化 0/30） |
| 权限 | 一次交互式 UAC；**不装内核驱动、不开 TESTSIGNING、不关 Secure Boot、不重启** |
| 实测 | 7 项断言全部 PASS：改写→`VK_RETURN`×4、改写→`VK_F13`×4、擦除生效、停止后恢复 |

**另一个坑：拦截是否生效，在 RC003 上根本无法观测。** 三键在 Windows 侧本来就零事件，"清掉"和"没清"在外面完全看不出差别。正主的解法是引入**哨兵键（canary）**——拿一个 Windows 本来能处理的键（主页 `0x4A`）做清空对象：运行前按它光标跳行首、运行中按它无反应、结束后恢复。这是判断"清空真的作用到了报告上"的唯一可复核判据。

### 3.4 这对你意味着什么

**少数派那套 macOS 方案里的"返回键 = Ctrl+C 中断"，在 Windows 上直接失效。** 而且这次是实测坐实，不是推测。

MVP 阶段别碰这条路——它要提权注入，复杂度和风险都高一个量级。先用这四条替代方案：

1. **用电源键（0xFF:0x5E）当中断键** —— 非标码，不与实体键盘冲突，已验证可穿透低级钩子
2. **用双击确认键**替代中断（就是你 YOOOCLAW 的双击逻辑）
3. **长按另一个可用键**
4. 放弃"中断"，改成"语音说'取消'"——反正你已经嘴对着麦了

等 MVP 跑通、确认你真的需要第三颗键，再回来走 3.3 那条路。

## 四、六个必踩的坑（附解法）

这六条是 mi-input 用踩坑换来的，每一条都可能让你卡一整天：

### 坑 1：SendInput 注入的 Ctrl+Win，微信输入法不认

> **IME 带 UIAccess 权限，SendInput 发的 Ctrl+Win 无效；物理按键有效。**

这是 Windows 输入权限体系的老问题：高完整性级别的进程不接收 UIAccess 较低的进程注入的输入。

**解法（很脏但有效）**：`PostMessage` 直接点击微信输入法状态栏窗口的麦克风按钮
- 窗口名：`wetype.statusbar.window`
- 麦克风按钮位置：宽度 45/142 处
- 语音面板 = 标题含"语音输入"的窗口
- 这是开关式的：按下开口 ∥ 松手再点一次闭口

**我的建议：这条链路太脆。** 依赖私有窗口名和像素坐标，微信输入法一改版就断。见第七节我的替代路线。

### 坑 2：解码后音量太小，被当静音

> 遥控器解码后峰值约 **-18 dBFS**，直通会被引擎判定为静音。

**解法：加 ×5 增益。**

### 坑 3：keymap 全局生效，无法区分设备来源

> 映射标准键码（0x24 / 0x5D / 0xC0）会连带影响实体键盘同名键——**低级钩子（WH_KEYBOARD_LL）无法区分输入来自哪个设备**。

**解法：优先用非标码**（如电源键 0xFF:0x5E），或者用 **Raw Input（RAWINPUTDEVICE）** 做设备路径限定——SayAll 的 `crates/sayall-windows/src/raw_input.rs` 就是干这个的，这是它比 mi-input 强的地方：**能从硬件设备路径层面区分输入来源，而不是靠低级钩子全局拦截。**

### 坑 4：ADPCM 解码状态不连续会有爆音

每次会话开头收到 `DecoderSync`，必须用它给的 `predictor` / `step_index` **重置解码器**。帧之间也要传递状态。

### 坑 5：IME 状态

vbridge 模式必须保证"微信输入法处于激活状态 + 系统默认麦克风 = CABLE Output"。任何一个被其他操作改掉，链路就静默失败——**不报错，就是不出字**。

### 坑 6：系统睡眠 / 蓝牙掉线

> SayAll 的做法值得抄：**2~30 秒指数退避自动重连，Windows 睡眠时释放会话、唤醒后重建 GATT + ATVV 会话。**

## 五、技术栈怎么选

| 方案 | 门槛 | 优点 | 缺点 | 适合你吗 |
|---|---|---|---|---|
| **Python + ctypes**（照 mi-input 路线） | 最低 | 零第三方依赖，改一行跑一行，**AI 迭代最快**，BLE 读写全部用 ctypes 搞定 | 性能一般（够用）、打包体积、托盘 UI 要自己画 | ★★★★★ **建议 MVP 用这个** |
| Rust + Tauri 2 + Vue 3（照 SayAll 路线） | 高 | 成品级 GUI、可视化映射、性能好 | 编译慢、改一处等半分钟，AI 迭代效率明显下降 | ★★★ 验证完习惯后，想要好看再迁移 |
| C# / WPF + WinRT | 中 | Windows 原生 BLE API 体验好 | 生态参考最少 | ★★★ 折中选项 |
| ESP32 硬件中继（BleRemoteBrideg 路线） | 高 | 能绕开 PC 端解码 | 延迟 100-200ms，还要重写 BLE 层 | ★ 不建议，除非你想造硬件 |

**我的建议：先 Python 跑通，再考虑要不要用 Rust 重写。** 原因是你这个项目的本质是"快速验证交互习惯"，不是"做产品"。用 Tauri 你会把 70% 时间花在编译和打包上，而不是思考"这个键应该映射成什么"。

## 六、关于 deepseek-harness：顺便说清楚它是什么

我核了一下仓库（默认分支是 `master`，所以 raw/main 抓不到）：

- **Star 238,464，MIT，TypeScript**，2026-08-13 建仓，今天还在推送
- 口号：**"DeepSeek Harness: Everything is a Plugin."**
- 它不是"某个 coding agent 产品"，而是**插件化的 Agent 运行时底座**：宿主层（`dsh` CLI + agent loop）→ 插件层（基于 cordis 插件容器）→ 适配层（ADR 0010 **twin LLM adapters**）
- 关键架构：ADR 0009 **capability seams**（能力接缝）+ ADR 0010 双 LLM 适配器
- 形态：Web（官方主推的 onboarding 路径）+ Desktop（Electron）+ Python runtime
- **内置 `demo:coding`，明确是 Coding Agent 场景**

最有意思的一点，也和你正在做的事直接相关：

> 它把 skills 放在 `.agents/skills`（例如 `dsh-code-review`），**通过 gitignore carve-out 的方式用 `.claude/skills` 符号链接暴露给 Claude Code 使用**。

也就是说，**Harness 的能力本来就被设计成可以喂给外部 Coding Agent 消费的**。如果以后你想把"遥控器 → Agent"这件事产品化，做成 Harness 的一个 plugin/skill 是这个生态里的原生做法，而不是另起炉灶。这个先放个书签，等你的遥控器软件跑通再说。

## 七、一条我认为更好的路线（建议认真考虑）

现有所有项目都走同一条链路：

```
ATVV 解码 → VB-CABLE 虚拟声卡 → 输入法/听写软件 → 文字进输入框
```

这条路有三个绕不开的东西：

1. **依赖 VB-CABLE** —— 它是捐赠软件，商用要授权，还会改你的系统默认音频设备
2. **依赖输入法的私有窗口名和像素坐标** —— 微信输入法一改版就断，且 Win11 状态栏渲染经常变
3. **链路长导致失败静默** —— 中间任何一环断了，表现都是"没声音/没字"，很难调试

**我建议你走这条更短的：**

```
ATVV 解码 → 本地 whisper.cpp 或云端 ASR → 自己后处理 → SendInput 直接打字到焦点窗口
```

理由：

- **三大依赖全部去掉**，链路短到可以逐环节肉眼验证
- **中英混输、代码术语词典、去口头禅**，全在你自己手里 —— 这才是 Web Coding 真正需要的（说"把这个函数改成 async"不会被转成"把这个帆船改成 a sync"）
- **可以直接做"选中即重写"**：检测到焦点窗口有选中文本时，语音内容当成编辑指令，这比单纯打字进 AI 输入框更有价值
- mi-input 已经验证过 whisper 引擎可行（它的 `stt.py` 是 whisper.cpp 子进程封装，base 模型精度偏弱但 small 可用）

> 补充一个判断：对"按住说话 — 松开出字"这种异步听写场景，**延迟完全不敏感**（你不需要实时监听自己的侧音）。所以本地 whisper small 完全够，不必纠结实时性。

## 八、分三期路线图（可以直接开干）

### 第 0 期：先验硬件（半天）

别急着写代码。先做这三件事，**顺序不能乱**：

| 步骤 | 做什么 | 为什么 |
|---|---|---|
| **① 先重配对** | Windows 蓝牙设置里删掉 RC003-MS，重新配对 | 初次配对只有 55% 送达率，会让你误判成"代码有问题"。**这一步不做，后面所有调试都是在错误基线上进行** |
| ② 确认 ATVV 存在 | 手机 nRF Connect 连上，看有没有 service `AB5E0001-...` | 排除固件版本差异 |
| ③ 拿第一份真实音频 | 跑通 `wangyl/mi-input`，或直接上正主仓库现成的 `Testing/probe-rc003-hid-gatt.ps1` / `probe-rc003-vendor-gatt.ps1` 枚举 GATT | 建立对照基准 |

**这一步的意义**：把"硬件个体差异 / 固件版本 / 配对态"这三个最大的未知数前置解决。后面所有代码才有对照基准。

> 有现成的就不要自己写：正主仓库 `hardware/RC003/evidence/` 下有一整批真机枚举日志（`gatt-probe-enum.log`、`gatt-probe-listen1.log`、`driverstack.out`、`all-hid-tlc.txt`），**等于别人替你踩过的现场记录**。先对着看你的枚举输出是否一致，不一致再从这里查。

### MVP 期：能打字（1-2 天）

目标：按住语音键 → 松开 → 文字落在当前窗口。

```
1. BLE 连接 + 设备识别（Model Number 0x2A24，或直接用 ATVV service UUID 枚举）
2. MTU 协商到 247            ← 卡住就先查这里
3. ATVV 握手 + Capabilities 解析
4. 订阅 AUDIO 通知，收集原始字节
5. IMA ADPCM 解码（注意：高 nibble 先、帧间状态连续、DecoderSync 重置）
6. ×5 增益
7. dump 到 WAV 文件，人工听一遍  ← 里程碑确认点
8. 接 whisper.cpp 转文字
9. SendInput 打字到焦点窗口
```

**验收标准**：对着终端说一句话，字出现在命令行里。

### v1 期：能控制（再 1-2 天）

```
10. Raw Input 设备路径过滤（只听这一台遥控器，不污染实体键盘）
11. 按键映射：电源键=中断、确认键=Enter、方向键×4=切换
12. 单击/双击/长按 三层语义（Windows 上这是刚需，因为可用键少）
13. 托盘常驻 + 开机自启
14. 断线指数退避重连（2-30s）+ 睡眠恢复
15. 诊断日志（每帧数没了、每会话耗时都记下来）
```

### v2 期：才考虑好不好看

```
16. 配置文件化管理快捷键（JSON/TOML）
17. 按焦点应用切换 profile（终端 / IDE / 浏览器 各一套）
18. 一段时间后再决定是否用 Tauri 做 GUI —— 到时候你已经有真实使用数据，
    知道哪些功能真的在用，哪些是假需求
```

## 十、几个判断

1. **不要逆向 ATVV。** 协议规格已经在开源项目的单元测试里摆着了，直接抄规格比逆向快一个数量级。这份规格是当前能拿到的最完整的公开版本。

2. **MVP 用 Python ctypes。** 你的目标是验证"要不要用嘴写代码"，不是跑 AST.perf。AI 帮你改一行就跑，这比 Rust 每次等编译重要得多。

3. **跳过 VB-CABLE。** 自己转写、自己打字，链路短三个数量级，可控性高。这是我觉得你的软件真正能比现成方案强的地方——不是"也能用"，而是"代码术语识别准"。

4. **键位规划要早做。** 返回键和音量键在 Windows 上死了，你只有「语音键 + 确认 + 4 方向 + 电源」共 7 个可用输入。把双击/长按规划进去，能撑出 20 个语义。

5. **先跑通别人，再自己写。** 不是为了偷懒，是为了给自己的实现找一个"已知可用"的对照基准。拿到知道自己硬件个体的行为之后，你的每一行代码都有参照。
