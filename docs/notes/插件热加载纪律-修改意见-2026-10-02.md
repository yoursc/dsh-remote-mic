## 0. 为什么需要这条纪律（事故复盘）

同一天里出了两次事故，**都不是能力问题，而是"改之前没有取证与失败半径评估"**：

| # | 我做了什么 | 实际后果 | 我当时的错误假设 |
|---|---|---|---|
| A | 用户说浮层关不掉，我加了一层全屏透明 `backdrop` 想"确保点外面一定关得掉" | 宿主页面**整页点不动**，用户只能刷新才恢复 | 以为是"事件相位/监听被拦"的问题 |
| B | 连改三轮（click 语义 → 捕获阶段 pointerdown → backdrop），每轮都直接推给正在使用的界面 | 用户被反复打断，最后要求把插件从 profile 摘掉 | 以为病因在关闭逻辑本身 |

**B 的真因**（当天最后定位）：`var open = React.useState(false)` —— 拿到的是**数组**（恒为真），
且 `setOpen` **从未定义**。于是浮层一挂载就永远渲染，而所有"关闭"路径都在调用一个不存在的函数，
异常被吞、静默失败。三轮改动全部建立在"关闭逻辑写错了"这个未经验证的假设上。

**两个共同点值得写进纪律**：

1. **没有一次先取证**。当天其实有现成的取证手段（页面加载的是哪个 rev、DOM 里是否残留旧实例、
   点击事件是否到达 `document`、控制台有没有 `ReferenceError`），一次都没用。
2. **热加载把每一次半成品都直接打进用户正在用的界面**。这个项目没有"编译期"这道缓冲。

## 1. 背景事实：本项目的插件是"活体"开发（先摆证据）

- 插件以 `link:` 装进 profile ⇒ **改文件即改正在运行的插件**（`/workspace/dsh-remote-mic/dsh-plugin`）。
- 宿主侧 `@deepseek-ai/dsh-client-hmr` 每 500 ms stat 轮询每个客户端 bundle，变了就
  `clientModules.rebuilt(id)`，再经 `/plugins/events`（SSE）把新 graph 推给浏览器 —— 实测抓到 `rebuilt` 帧。
- **浏览器侧是否就地替换不稳定复现**：2026-10-02 多次出现"宿主已推送新 rev、页面仍在跑旧代码"。
  ⇒ 迭代一律**以硬刷新为准**，不许把"应该会热更新"当作验收条件。
- 结论：**插件的每一次保存都可能立刻作用在用户眼前的界面上**，这决定了下面的纪律是必要的，而不是形式主义。

## 2. 建议条文（可直接落进手册的正文）

### 2.1 改动前四步（缺一不可）

1. **取证**：症状落在哪一层（宿主 / 客户端 / 接缝 / 设备）？页面跑的是哪个 rev？
   有没有现成的观察点（`/plugins/events`、控制台报错、`performance.getEntriesByType('resource')`）？
   **在没有证据之前，不许改代码。**
2. **假设**：写明"我认为病因是 X"，并给出**能证伪它的最小观察**。
   假设与改动一起说给用户听。
3. **失败半径**：这个改动最坏会怎样？是否可能波及宿主页面（全屏层 / 全局监听 / 往他人 DOM 注入）？
   **半径无界（全屏元素、全局快捷键、改动他人节点）必须先取得用户明确同意。**
4. **单变量 + 回滚**：一次只改一处，用户验过再走下一步；动手前先把回滚路径备好
   （刷新 / `dsh plugin --profile web remove dsh-remote-mic-plugin` / profile 清单备份）。

### 2.2 硬红线（本次事故直接换来）

- **禁止全屏点击拦截层**（backdrop / 遮罩）：它一旦残留或被反复渲染，宿主整页点不动。
- **禁止在他人页面挂全局监听当"兜底"**：除非说清失败半径，且带明确退出条件。
- **React 状态必须解构**：`var pair = useState(x); var v = pair[0], setV = pair[1];`。
  绝不出现"数组/对象当布尔用"的写法。
- **关合类 UI 优先用框架原语**，不自造：
  `@deepseek-ai/dsh-client-ui-primitives` 的 `Tooltip(openOnClick)` /
  `useDismissOnOutsidePointer` / `useAnchoredPosition`；官方「会话统计」面板用的就是后两者。
- **改任何交互前，先问"这会不会影响宿主页面"**；答案为"可能"时，先要授权。

### 2.3 验证闭环（交付前三条自检）

1. `node --check <改动的文件>`；
2. 从**运行中的实例取回真实产物**再跑一遍回归（不是只测工作区文件）；
3. 纯逻辑要有无硬件断言；**接线类**（状态、事件、注册）要有无浏览器回归 ——
   本次实证：这类 bug 只有这种测试能抓到（对原始提交版本 FAIL ①②，对修复版本 15/15）。

### 2.4 热加载的使用纪律

- 改完先说清"这次要让用户看什么、怎么算通过"；
- **用户正在使用界面时，不在同一轮里连改多处**；
- 一旦出现"关不掉 / 点不动"这类**阻塞性**症状：**先给回滚路径，再谈定位**；
- 每次改动前提醒用户"改完请硬刷新"，别指望热替换。
