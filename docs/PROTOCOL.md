## 0. 一句话

一个本机常驻 local-mic，把**任意语音输入硬件**归一成一条**与设备无关**的音频流，
经 `ws://127.0.0.1:8787` 提供给浏览器侧消费（dsh 插件 / 诊断页）。

```
   硬件                    local-mic（本机常驻）              消费侧
┌──────────┐          ┌──────────────────────┐        ┌──────────────┐
│ 遥控器    │──BLE────►│ 采集 · 解码 · 会话机 │──ws──► │ dsh 插件     │
│ 蓝牙麦克风│──HFP────►│ 归一为 PCM16 16k 单  │        │ 诊断页       │
│ 键盘热键  │──本机────►│ 设备识别 · 电量      │        │ （N 个客户端）│
└──────────┘          └──────────────────────┘        └──────────────┘
```

**客户端不知道线的另一头是什么。** 遥控器、蓝牙耳机、脚踏开关，在接缝上长得一样。

## 1. 三条设计原则

规范里每一条看似多余的约束，都源自这三条之一。有疑问时回到这里。

### 原则 1 · 接缝用设备无关词汇

接缝上**不得出现**：BLE UUID、GATT 特征、ATVV opcode（`0x08`/`0x04`/`0x00`/`0x0B`/`0x0A`）、
设备命令（`0x0C`~`0x0E`）、`session_id`、帧大小（120 字节）、ADPCM 或任何具体编码名。

判定标准很简单：**这个名词换一台设备还在吗？** 不在的，就不属于接缝。

### 原则 2 · 显式优于静默

版本不匹配要**明确拒绝并断开**，不支持的音频格式要**明确报错**，而不是"警告后继续"或"尽力而为"。
本项目的失败模式特征是**静默**：没有报错，只是结果不对（转写乱码、丢半个字、音量跳变）。
规范里每条"必须报错"都是针对一次已发生的静默故障。

### 原则 3 · 控制流单向

**客户端不发送任何设备命令。** 插件 → local-mic 只有 `hello` 一种消息。

这在物理上是成立的：ATVV 的流程本来就是**设备主动发起**（设备发开麦请求 → 主机应答）。
所以开麦、续期、关麦天然全属于 local-mic，客户端从不需要发命令。

副作用是好的：**"多客户端谁能控制设备"这个歧义从根上消失了。**

**两个曾经"能工作"但违反原则的字段**：`ready.uuids` 把 ATVV 三个特征 UUID 泄到接缝上（违反原则 1），`{op:"write"}` 让客户端能发设备命令（违反原则 3）。
它们不是因为坏了才被删，而是因为接缝的词汇层级不对 —— **别再以"方便"为由加回来。**

## 2. 传输层

| 项 | 约定 |
|---|---|
| 协议 | WebSocket（RFC 6455 子集：握手 + text + binary + ping/pong + close） |
| 监听 | 仅回环 `127.0.0.1`，**不得绑定 `0.0.0.0`** |
| 默认端口 | `8787`（走 `HKCU\Software\DshRemoteMic\Port` 可改） |
| 客户端 → local-mic | **只有文本帧**（JSON）。二进制帧**忽略** |
| local-mic → 客户端 | 文本帧（JSON）+ 二进制帧（音频） |

### 2.1 连接建立失败（客户端行为约定）

**⚠ 这不是一条消息。** local-mic 未运行时**不存在任何连接**，因此"local-mic 没起来"这件事
**无法**通过接缝表达——任何为它定义错误码的做法都注定送达不了
（这正是 `port_in_use` 被移出 §9.1 的原因：端口被占用 ⇒ WS 服务端没起来 ⇒ 广播给零个客户端）。

客户端连不上 `ws://127.0.0.1:8787` 时（ECONNREFUSED / 握手超时），按以下约定处理：

| # | 约定 | 理由 |
|---|---|---|
| 1 | **判定为"local-mic 未运行或版本过老"，不是设备故障** | 两者给用户看的提示完全不同，别混为一谈 |
| 2 | **给人话提示**（"语音助手未运行，请先启动 local-mic"），不展示 Windows 异常原文 | 面向用户的文案由客户端写（§9） |
| 3 | **指数退避重试**（如 1s → 2s → 4s → 上限 30s） | 不要密集重连刷日志 |
| 4 | **不得**按 `retryable:true` 的语义"安静等待" | local-mic 没装时安静等待 = 用户永远不知道缺了什么 |

local-mic 侧的对应义务：**端口被占用、或已有实例在运行时，在本地 UI 呈现**
（托盘气泡 / 主界面提示"已在运行"或"端口 8787 被占用"）——**不产生任何接缝消息**。

## 3. 消息总览

| 方向 | 形式 | 名称 | 作用 |
|---|---|---|---|
| C → H | JSON | `hello` | 握手 + 声明订阅 |
| H → C | JSON | `ready` | 握手应答：**我们能怎么通信** |
| H → C | JSON | `device` | **现在连着谁**（身份与属性） |
| H → C | JSON | `state` | 链路粗略状态（**机读枚举**，可用于 UI 门控） |
| H → C | JSON | `capture` | 采集窗口的边界 |
| H → C | JSON | `error` | 结构化故障原因（给程序看） |
| H → C | binary | `0x02` | 音频采样 |

`ready` 与 `device` 的分工是刻意的，别合并：
**`ready` 回答"协议能力"，`device` 回答"设备身份"**，两者的变化时机完全不同
（前者一次连接一次，后者随 DIS 读出、电量推送、设备切换而变）。

## 4. `hello`（客户端 → local-mic）

```json
{ "op": "hello", "proto": 1, "audio": true }
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `op` | ✓ | 固定 `"hello"` |
| `proto` | ✓ | 整数。不匹配 → local-mic 回 `error{code:"proto_mismatch"}` 并**关闭连接** |
| `audio` | — | 是否接收音频采样帧。**缺省 `true`**（即订阅） |

> ⚠ **`hello` 没有 `caps` 字段** —— 曾设过（客户端能力），2026-09-29 删除。
> 理由见 §6：**`caps` 是单向的，只有 `ready.caps`。**

**语义**：

1. **幂等，可重复发送，以最后一次为准。** 改主意只需再发一次
   （想退订就发 `audio:false`，想恢复就再发 `audio:true`）。
   **不设独立的 subscribe/unsubscribe 消息** —— 消息类型是 schema 里最贵的东西。
2. **订阅状态是 per-connection 的，随连接消亡。** 断了就要重新声明。
   于是"重连后默认值"这个问题不存在（没有历史状态要记），
   也挡掉一类故障：上次退订了、这次连上莫名收不到音频。
3. **附带副作用**：`hello` 触发一次连接尝试（若尚未连接）。这保留了 proto 0 的既有行为。
4. `audio:false` **只关音频采样帧**。`state` / `device` / `capture` / `error` **照常发送**
   （每次 capture 才两条、几十字节，成本可忽略；且任何客户端都需要知道"正在录音"）。

### 4.1 连接建立后的消息时序

```
TCP 连接建立
   │
   ├─ L→C  state（补发当前状态）        ← 可能在 hello 之前
   ├─ L→C  device（若已知）             ← 可能在 hello 之前
   │
C→L  hello
   │
   ├─ 校验失败 → L→C error{proto_mismatch} → 关闭连接
   └─ 校验通过 → L→C ready ──► 此后才可能推送音频帧 / capture
```

1. **客户端不得假设第一条消息是 `ready`。**
   `state` / `device` 会在连接建立后立即补发（§8.1 的补发语义是刻意为之）；
   而 `hello` 还会触发一次连接尝试（§4 语义 3），所以 `ready` 之前可能夹着 `state:connecting`。

2. **local-mic 在收到合法 `hello` 之前，不得推送音频帧。**

   ⚠ 这条是为了裁决一个自相矛盾：§4 说 `audio` 缺省 `true`（订阅），
   §6 说 `proto` 必须先校验 —— 在连接建立的那一刻两者是打架的。

   **"缺省订阅"的准确含义是「收到不带 `audio` 字段的 `hello` 时视为订阅」，
   不是「连接建立即订阅」。**

   不澄清的话，照"缺省 true"实现会在握手完成前就开闸。而这个错的症状是**良性的**
   （老客户端照样收得到），于是它会一直潜伏到 proto 2 出现那天才暴露 ——
   典型的 E 类静默故障形状。

3. **重发 `hello` ⇒ 重发 `ready`。** 两端都幂等，客户端可随时重新确认协议能力与格式描述符。

4. **进行中的 capture 对新连接完全不可见。**
   不补发 `start`，也不补发它的音频帧与它的 `end`；该连接从**下一段**开始才可见。
   理由：§8.2 保证 `start` / `end` 成对出现。给中途连上的连接补一个没有 `start` 的 `end`，
   会让客户端的封段逻辑收到孤儿事件。

5. `state` / `device` / `error` **不受第 2 条约束** —— 它们在握手前就该送达，
   这样即使 `proto` 不匹配，客户端也知道"连上了，但版本不对"。

### 4.2 C→L 消息的处理动作（分级）

"拒绝"这个词太模糊，此处把动作写死：

| 情况 | 动作 |
|---|---|
| JSON 语法错误 / 客户端发来**二进制帧** | **关闭连接**（不回 `error`） |
| `hello` 缺 `proto` 或不匹配 | `error{code:"proto_mismatch"}` + **关闭**（§6） |
| **被删除的 op**（如 proto 0 的 `write`） | `error{code:"op_not_supported"}` + **保持连接** |
| **真·未知 op** | **静默忽略** + 记录告警 |
| 字段类型错误（如 `audio` 不是布尔） | 按该字段**缺省值**处理 |

**前两条的理由**：WebSocket 有消息边界，坏 JSON 不是"粘包"造成的——
它只能说明对端不是本协议的客户端（或有严重 bug），继续会话没有意义。

**为什么 `write` 不按"未知 op"忽略**：它与不变量 8 的"忽略未知"**并不冲突**——
那条针对的是**演进新增**的东西，而 `write` 是原则 3（单向控制流）亲手删掉的。
两者安全上等价（都不执行设备写入），差别只在**可观测性**：
回 `error` 能让"有人日后误把 `write` 接回去"立刻暴露，静默忽略不能。

**`error.code` 的值域是开放的**（新增值不需要抬 `proto`）。
这与 `reason` 值域封闭（§8.2.2）**不对称，且是有意为之**：

| | 值域 | 未知值的兜底 | 结论 |
|---|---|---|---|
| `reason` | **封闭** | "不送转写" ⇒ **静默丢字**，代价太大 | 必须靠 `proto` 拦 |
| `error.code` | **开放** | 按 `retryable` 决定行为 ⇒ 客户端仍能正确应对 | 不需要拦 |

## 5. `ready`（local-mic → 客户端）

```json
{
  "op": "ready",
  "proto": 1,
  "caps": [],
  "audio": { "format": "s16le", "rate": 16000, "channels": 1 }
}
```

| 字段 | 说明 |
|---|---|
| `proto` | 整数。客户端必须校验，不匹配则**主动断开并报错** |
| `caps` | local-mic 能力，字符串数组、**只增**（见 §6） |
| `audio.format` | 固定 `"s16le"`。这个名字已同时表达位深（16）与端序（小端），**不再加 `bits`/`endian`**（多一个字段多一处能漂的地方） |
| `audio.rate` | 整数采样率。v1 只允许 `16000` |
| `audio.channels` | 声道数。v1 只允许 `1` |

**发送时机**：连接建立后、`hello` 校验通过时。
若此刻设备尚未连上，`ready` **仍应发送**（协议能力与设备是否存在无关），
客户端随后会通过 `state` / `device` 得知设备情况。

## 6. 版本协商

**规则**：`proto` 是整数，**只在破坏性改动时递增**；不做范围协商、不做协商降级。

- 不匹配（包括**缺 `proto` 字段** ⇒ 视为 `proto 0`）→ **明确报错并断开**
- 双向校验：local-mic 校验 `hello.proto`，客户端校验 `ready.proto`
- 拒绝时发 `error{code:"proto_mismatch", retryable:false}` 再关闭，
  **不要**"警告后继续"

**`caps` 与 `proto` 的分工**（这是这套机制能长期活着的原因）：

| | 何时变 | 对老客户端的影响 |
|---|---|---|
| `proto` | **破坏性**改动 | 老客户端被拒 —— 这是对的，因为它真的解析不了 |
| `caps` | 加功能（**只增**） | 老客户端忽略不认识的能力项，照常工作 |

只有 `proto` 一条会越走越尴尬：local-mic 每加一个功能就得抬版本号，老插件被无谓地拒之门外。
`caps` 是给那个场景准备的。

> ⚠ **`caps` 是单向的 —— 只有 `ready.caps`，没有 `hello.caps`。**
>
> `hello.caps`（客户端能力）曾设过，2026-09-29 删除。理由：
> **local-mic 的行为不随客户端能力变化**（协议单向，原则 3），
> 于是它**没有任何消费场景**，存在的唯一理由是跟 `ready.caps` 对称 ——
> 而"多一个字段多一处能漂的地方"正是本规范自己的原则（见 §5 关于 `bits`/`endian` 的说明）。
>
> 将来若真需要（例如协议放宽为可变采样率后，客户端声明它能接受哪些格式），
> **加回来是非破坏性的**：不变量 8 保证双方忽略未知字段，老实现照常工作。

### ⚠ 为什么这个版本号是"这次就得有"的，而不是预防性设计

本次改动里，音频二进制帧的**帧头 `0x02` 不变、帧长量级相近、含义全变**
（从 ADPCM 半字节变成 PCM16 样本）。

后果：老 exe + 新插件（或相反）→ 插件把 ADPCM 的半个字节当作一个 16-bit 样本读
→ **得到白噪声或极低沉的怪声，全程不报任何错**。
用户只会认为"转写坏了"，要排查很久才会想到版本不匹配。

**这类静默故障正是 `proto` 存在的理由。**

## 7. 消息：`device`（local-mic → 客户端）

```json
{
  "op": "device",
  "id": "C0:5D:39:F8:50:C7",
  "name": "小米蓝牙遥控器 2 Pro",
  "model": "RC003",
  "paired": true,
  "battery": 99
}
```

| 字段 | 说明 |
|---|---|
| `id` | 设备稳定标识（当前实现为 MAC）。**不透明**：客户端只可用来区分设备或记住偏好，**不得解析** |
| `name` | 面向用户的显示名。命中型号白名单时是友好名，否则回落设备自报名 |
| `model` | 设备自报型号，可为空字符串 |
| `paired` | 系统配对状态 |
| `battery` | 整数百分比；`-1` 表示未知。**是"最后已知值"，不保证新鲜**（见下） |

**发送时机**：① 新客户端连上且已有设备信息；② 设备信息发生变化（读到 DIS、电量推送、设备切换）。

**不包含"是否在线"** —— 那由 `state` 表达。

> ⭐ **`battery` 的新鲜度由 `state` 表达，接缝上没有第二个信号。**
> 设备断线后，客户端手里的电量就是断线前那次读数。
> 客户端应据 `state` 判断：不是 `connected` 时，电量视为不可信（如灰显）。
>
> 之所以**不**引入第二个信号源（断线时补发 `battery:-1`，或加时间戳字段）：
> 一旦"看 `state` 推断"与"显式 `-1`"并存，将来两者不一致时就没有裁决依据。
>
> **换设备是例外** —— 那时 `id` / `name` 已变，local-mic **必须**发 `device{battery:-1}`，
> 因为新设备的电量确实还没读到。这条路径是通的：`SetAddress` 会把电量清成 `-1`。

**注意**：设备**不包含任何 BLE/GATT 细节**（理由见 §1 原则 1）。

## 8. 消息：`state` 与 `capture`

### 8.1 `state`（local-mic → 客户端）

```json
{ "op": "state", "state": "connected", "detail": "已连接" }
```

| 取值 | 含义 |
|---|---|
| `disconnected` | 设备未连接（可能正在等重连） |
| `connecting` | 正在尝试连接 |
| `connected` | 设备已连接 |
| `error` | 处于错误态，**同时会收到一条 `error` 消息** |

- `detail` 是**人类可读的诊断文本，客户端不得解析它**（它的措辞随时会变）
- 判断具体故障请用 `error` 的 `code`，不要用 `state`+`detail`

#### 8.1.1 ⭐ `state` 是「状态」，不是「事件」

`state` 描述的是**当前是什么状况**，不是"刚刚发生了一次什么"。

| 规则 | 说明 |
|---|---|
| **只在取值变化时推送** | local-mic **必须做变化检测**。同一取值连续出现（典型：重连定时器每 5 秒重试失败一次）**不得**重复广播 |
| **新客户端连上时补发** | 不受上一条约束 —— 补发保证任何客户端在任何时刻都能拿到当前状态 |
| **客户端可依赖最新值** | "最后收到的 `state` 就是当前状态"，客户端**不需要自己从消息流推导** |
| **`connected` 只发一次** | 连接成功路径上不得重复广播（详见 §9.3） |

> 这条是 §9.2「`retryable:true` ⇒ 安静等待」能成立的**前提**：
> 若每次重连失败都刷一轮 `connecting` + `error`，客户端即便想安静，也被迫每 5 秒响应一次。

**抑制不会造成"客户端不知道 local-mic 死了"。**
WebSocket 跑在 TCP 上，local-mic 进程退出会触发 `onclose`——所以抑制**不需要心跳补偿**，
也不要以"怕客户端收不到"为由把重复发送加回来。

#### 8.1.2 `state` 是机读的，`detail` 是给人看的

| | 性质 | 客户端可以怎么用 |
|---|---|---|
| `state` | **机读**。值域**封闭**（上表四值即全部；新增值属破坏性变更，须抬 `proto`） | **可以依赖**：据最新值做 UI 门控（如非 `connected` 时禁用录音入口） |
| `detail` | 给人看。**不得解析**（措辞随时会变，可能是本地化的 Windows 原文） | 只能原样展示或记日志 |

> 这条修掉了一处自相矛盾：§3 消息总览曾把 `state` 写成"给人看"，而 §8.1 自己给出了封闭枚举。
> 按 §8.1.1 的状态语义，**它是机读的** —— 客户端能依赖它，正是状态语义要兑现的价值。
>
> 具体故障分类仍用 `error.code`，不要用 `state` + `detail` 去猜。

**三个枚举字段的值域口径不一致，是有意的** —— 按"未知值的兜底代价"分档：

| 字段 | 值域 | 未知值的 fail-safe | 代价 | 结论 |
|---|---|---|---|---|
| `reason` | **封闭** | 不送转写 | **静默丢字** | 必须靠 `proto` 拦 |
| `state` | **封闭** | 不做 UI 门控 | 用户在不能录音时点了按钮 | 靠 `proto` 拦 |
| `error.code` | **开放** | 按 `retryable` 决定行为 | 无损失（`retryable` 已提供完整语义） | 不需要拦 |

### 8.2 `capture`（local-mic → 客户端）

```json
{ "op": "capture", "phase": "start", "source": "remote" }
{ "op": "capture", "phase": "end", "reason": "released", "source": "remote" }
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `phase` | ✓ | `"start"` \| `"end"` |
| `reason` | 仅 `end` | `released` \| `timeout` \| `disconnected` \| `aborted` |
| `source` | — | 触发来源（`remote` / `hotkey` / …）。**值域开放，客户端不得依赖具体值做逻辑** |

**`source` 的用途**：**仅用于 UI 标注与日志**（例如"这句是从遥控器来的"）。
它是纯信息，**不得参与任何逻辑分支** —— 尤其不得出现"只有 `source=="remote"` 才送转写"这类判断。

v1 只有 `remote` 一个值。将来 local-mic 支持键盘热键等来源时新增取值，
因为值域开放，属**非破坏性**变更（不变量 8：客户端忽略未知枚举值）。

**`reason` 的用途**（这是必须有的字段，不是装饰）：

若 `end` 不带原因，客户端只能把**每一次**结束都当成"用户松手了"，
于是设备掉线的瞬间会拿半截音频去转写，**然后把错误的文字注入输入框**。

#### 8.2.1 `reason` 的精确触发条件

| reason | 触发条件（local-mic 侧判定） | 客户端**建议**（不是指令） |
|---|---|---|
| `released` | 用户松开输入源，且**无**下列异常迹象。判定依据：设备 `0x00` StreamStopped **或**音频静默超时（二者谁先到谁生效，见 §8.2.4） | **送转写** |
| `timeout` | **`start` 之后**，在 local-mic 设定的合理窗口内**未收到任何音频帧** | **不送**（空转写只会产生垃圾文字） |
| `disconnected` | `start` 之后 BLE 连接断开 | 可用部分仍可送转写，**但应提示不完整** |
| `aborted` | local-mic **主动终止**（如达到自身最大录音时长），或**被设备掐断**（见 §8.2.3） | 同上 |

> **为什么第三列是"建议"而不是"指令"**
> "丢不丢"是客户端的**交互决策**，不是接缝事实；接缝只负责说清"发生了什么"。
> 典型例子：`aborted` 时被掐断之前那几秒音频是**完整可用的**，一律丢弃反而浪费。

**`timeout` 必须是 `start` 之后的事件。**
等待按键超时（用户还没按下）**不产生任何 `capture` 消息** —— `start` / `end` 必然成对，
没有 `start` 就没有 `end`，自然也带不了 `reason`。那属于 local-mic 内部等待，不在接缝上。

#### 8.2.2 `reason` 值域是封闭的

上表四个值即全部。**新增 `reason` 值属破坏性变更，必须抬 `proto`。**

理由：`reason` 直接决定客户端"送不送转写"（不变量 8：未知 `reason` ⇒ 不送转写）。
若值域开放，将来新增一个表示"正常结束"的值，老客户端会按 fail-safe 判为**不送** ⇒ **静默丢字**。
**封闭 + 抬 `proto`** 是唯一不会静默出错的组合。

#### 8.2.3 `aborted` 的判定是启发式的 —— 规范不承诺精确

固件免费音频窗口约 **5.7 秒**，超过即被精确掐断；local-mic 必须每约 2.5 秒发 `0x0E` 续期
（见 `AGENTS.md` §4.6 坑 2）。

设备被掐断时发的仍是 `0x00` —— **与用户松手的字节完全相同，无法从 CONTROL 区分**。
⇒ local-mic 只能依据"最近一次 `0x0E` 写入是否失败"这类间接迹象推断。

**规范不承诺这个判定是精确的**，但保留这个名字：
5.7 秒被掐断时若谎报 `released`，用户会**静默丢掉音频尾部且毫无线索** ——
宁可有一个启发式的 `aborted`，也不要没有它。

**配套要求**：续期写入失败时 local-mic 必须发 `error{code:"write_failed"}`，
让客户端至少知道"这一段可能不完整"。

#### 8.2.4 `0x00` 会迟到 —— 必须有静默兜底，`reason` 不变

真机实测（2026-09-29）：松手后 `0x00` **不按时到达**，往往要等下一次按键才随连接激活
一起投递 —— BLE 空闲时连接间隔变大，通知要等下一个连接事件。

⇒ local-mic **不得只等 `0x00`**。必须以"音频停够 600 ms"作为并行的结束判据，
二者**谁先到谁生效**；迟到的 `0x00` 到达时窗口已关，直接忽略（不产生第二次 `end`）。

`reason` 语义**不变**：静默判定的是同一件事（用户松手），不是新的失败模式，
仍报 `released`。接缝因此无需改动 —— 这正是把硬件怪癖收在 local-mic 内的意义。

看门狗只在**收到首帧之后**才启动，否则会抢在 `timeout` 之前把"开麦后零音频"
误判成 `released`（见 §8.2.1 `timeout` 那一行）。

**`phase: "start"` 与 `phase: "end"` 必然成对出现。** 客户端只需处理这一对之间的音频帧。

## 9. 消息：`error`（local-mic → 客户端）

```json
{ "op": "error", "code": "pairing_required", "retryable": false,
  "message": "Authentication failed" }
```

| 字段 | 说明 |
|---|---|
| `code` | 稳定的机器可读常量，见下表 |
| `retryable` | **比 `code` 本身更重要** —— 决定客户端"安静等待"还是"提示用户动手" |
| `message` | 诊断兜底（可能是 Windows 原文）。客户端**已知 `code` 时不应展示它** |

> ⚠ **没有 `args` 字段**（曾以 `{"port":8787}` 为例，2026-09-29 删除）。
> 它具备"死字段"的全部特征：**8 个 code 无一定义过它的 key**，而唯一示例随
> `port_in_use` 的移除（见 §9.1）已失去消费场景。
> 更硬的理由是：**开放字段 + 无人守门 = 原则 1 的敞开口** ——
> 最容易被塞进去的恰是硬件细节（`write_failed` 带 ATVV opcode、`pairing_required` 带 GATT 状态码）。
> 唯一 plausible 的消费场景（`unsupported_device` 带 `{rate:48000}`）也被原则 1 自己驳倒：
> 客户端不该认识采样率背后的设备，它只需要"不支持"这个事实。
> 将来若确需，加回来是**非破坏性**的（不变量 8：客户端忽略未知字段）。

**面向用户的文案由客户端写**，因为面向用户的是客户端。local-mic 只提供事实。

### 9.1 错误码表

| code | 触发条件 | `retryable` | 要用户动手 | local-mic 会自愈 |
|---|---|---|---|---|
| `pairing_required` | BLE 链路未配对（ATT 0x05） | `false` | 要 | ✗ |
| `unsupported_device` | 设备不支持所需音频格式（如非 16 kHz） | `false` | 要 | ✗ |
| `proto_mismatch` | `hello.proto` / `ready.proto` 不匹配 | `false` | 要（更新插件或 exe） | ✗ |
| `op_not_supported` | 客户端发了被删除或不支持的 op（如 proto 0 的 `write`） | `false` | 不要（客户端实现问题） | ✗ |
| `device_not_found` | 找不到已配对的设备 | `true` | 可能 | **✓** |
| `connect_timeout` | 连接超时 | `true` | 可能 | ✓ |
| `disconnected` | 运行中掉线 | `true` | 不要 | ✓ |
| `write_failed` | 向设备写入失败 | `true` | 不要 | ✓ |

> ⚠ **`port_in_use` 不在此表中**（曾位列第一，2026-09-29 移除）。
> 端口被占用 ⇒ WS 服务端没起来 ⇒ 没有连接承载这条消息 ⇒ **物理上不可能送达**。
> 它是 local-mic 的**本地故障**，由本地 UI 呈现，不是接缝错误码。
> 客户端对应的真实场景是"连不上"，见 **§2.1**。

### 9.2 ⭐ `retryable` 为什么是关键字段

local-mic **本来就在自动重连**（有客户端时约 5 秒一次，无客户端时约 30 秒一次）。

所以 `device_not_found` **不是错误，而是"暂时状态"** —— 遥控器放远了、没开机、没电了，
local-mic 自己会一直试。

客户端如果不知道这件事，就会在用户只是把遥控器塞进抽屉时弹出一个红色错误框。
`retryable: true` 的语义就是：**安静等待，不要打扰用户**。

### 9.3 发送时机：`error` 同样只在变化时推送

`error` 与 `state:"error"` 配对，同为**状态语义**。判据在此写死：

| 情况 | 是否发送 |
|---|---|
| 从无错误 → 出现错误 | **发** |
| 错误的 `code` 发生变化 | **发** |
| **同一 `code` 连续出现**（如重连定时器反复失败） | **不发** |
| 错误消失（恢复为 `connected`） | 不发 `error`，由 `state` 表达 |
| 新客户端连上，且当前正处于错误态 | **发**（补发，不受上表约束） |

> 判据写死是为了避免各实现自己定义"什么算变化"。
> 最容易产生分歧的是"同一 `code` 的重复重连失败算不算变化"——答案是**不算**。
> local-mic 的自愈是常态（§9.2），把它当事件推，等于让客户端为一件它本该忽略的事反复响应。

**配套要求**：连接成功路径上 `connected` **不得重复广播**。
典型错误是"连接流程里发一次 + 连接状态变更事件里再发一次"——按状态语义，这两次取值相同，只应发一次。

## 10. 二进制帧：音频（local-mic → 客户端）

```
┌────────┬──────────────────────────┐
│ kind   │ payload                  │
│ 1 byte │ 变长                     │
└────────┴──────────────────────────┘
```

| kind | 名称 | payload |
|---|---|---|
| `0x02` | audio | **PCM16 s16le 样本流**（见 §11） |

- proto 1 **只定义 `0x02`**。其他 kind 值一律视为协议异常：**忽略并记录一次告警**
- `0x02` 的载荷长度**必须为偶数**（PCM16 样本为 2 字节）
- 当前实现每帧约 15 ms（480 字节），即约 32,000 B/s，**但客户端不得依赖帧大小或帧率** ——
  帧边界不承载任何时间语义，客户端应按字节数自行累积（见不变量 5）

> **proto 0 的 `0x01`（控制事件原始字节）已删除。** 它字面上就是"把设备的控制字节转给客户端"，
> 违反原则 1。控制语义现在只以 `capture` 事件的形式出现。

## 11. 字节级约定

**这是静默漂移的高发区，逐条钉死。**

| 项 | 约定 |
|---|---|
| 样本格式 | 有符号 16 位整数（`int16`） |
| 端序 | **小端**（little-endian） |
| 声道 | 交织（interleaved）。v1 恒为 1 声道，故无区别 |
| headroom | **无约定**：满量程即 ±32767。local-mic 不做任何预留衰减 |
| 增益 | **v1 不做**。local-mic 原样输出设备采到的样本；客户端也不得施加任何增益。**见 §11.1**（禁令基于未验证前提 + 豁免 + 破坏性变更定义） |
| 容器 | **无容器**：裸样本流，**不带 WAV 头**。需要 WAV 时由消费侧自行封装 |
| 采样率 / 声道 | 以 `ready.audio` 声明为准 |

**v1 只接受 `rate=16000, channels=1`。** 设备给不出这个格式时，
local-mic 必须报 `error{code:"unsupported_device", retryable:false}` 且**不开始采集**，
而不是"尽力发出去"。理由：下游若静默按 16 kHz 解读 48 kHz 数据，得到的是
音调语速错乱、但**完全不报错**的转写结果。

> 将来接 48 kHz 设备时两条路都还开着，且**不需要现在选**：
> (a) local-mic 加重采样，让 `rate` 恒为 16000（位置合理，这就是设备适配）；
> (b) 协议放宽为可变 `rate` —— 但**前提是先验证下游确实按声明采样率处理**。

### 11.1 增益：禁令、豁免，与"将来若加"的性质

**v1 不做增益。** local-mic 原样输出设备采到的样本；客户端也不得施加任何增益——
更不得硬编码某型号的经验增益（那是把设备特性写进客户端，违反原则 1）。

**⚠ 这条禁令建立在未验证的前提上。** RC003 的原始电平约 −30.6 dBFS，
而"这个电平直接喂 ASR 够不够用"**尚未实测**：

| 场景 | 结论 | 验证状态 |
|---|---|---|
| 本地试听 | 电平偏低，需增益（经验值约 ×4.28） | ✅ 已实听 |
| ASR 转写 | −30.6 dBFS 是否够用 | ❌ **未验证** |

> ⚠ **两件事别混为一谈**：那个 ×4.28 的目标是"**归一到 −18 dBFS**"，
> 而 −18 dBFS 是**音频制作的常用电平**、给**人耳听**定的，不是给识别引擎定的。
> 它回答的是"听着够不够响"，**从未回答过"ASR 需不需要"**。别把它当 ASR 结论引用。

**豁免**：local-mic 的**本地试听播放**属展示用途，允许施加增益，不受此禁令约束——
它不产生、也不改变接缝上的任何字节。

**将来若要加增益，无论放在 local-mic 还是客户端，都属破坏性变更，必须抬 `proto`。**
理由：样本内容变了而 `proto` 未变 ⇒ 老客户端无从感知 ⇒ 这正是 §6 要防的静默漂移。

## 12. 接缝不变量（客户端可以依赖这些）

1. **只出现有效音频。** 接缝上的音频采样必属于某个已 `start` 且未 `end` 的采集窗口。
   窗口外的音频**不得**出现在接缝上，无论设备是否提供。
   两种设备的差别只在**谁做门控**：遥控器是设备自己不开麦，常采设备（热键+麦克风）是
   local-mic 主动丢弃。**接缝上两者形状完全一致** ⇒ 客户端逻辑极简：
   收到 `start` 就开始收，收到 `end` 就封段，不需要判断音频有没有效。

2. **`end` 之后不再出现属于本段的音频。**
   实现要求：local-mic 收到停止信号后再等一个约 30 ms 的收尾窗口，然后才广播 `end`。
   （原因：音频与控制是两个独立通道，**到达顺序不保证**，末帧可能排在停止信号之后。
   若客户端一收 `end` 就封段，症状是**每句话结尾丢半个字**，极难排查。）

3. **客户端不得假设自己是唯一接收者。** 每个连接独立收到完整流。
   "后台标签页要不要处理这段音频"是客户端自己的策略（例如判断页面可见性），
   由协议规定是错位的：那是消费侧的选择，不是生产侧的事实。

4. **控制流单向。** 客户端不发送设备命令，也没有任何"写"通道。

5. **帧边界不承载时间语义。** 音频帧大小与到达节奏是实现细节，客户端按字节累积。

6. **事件不受音频订阅影响。** `audio:false` 只停音频采样帧。

7. **客户端只处理 `start` 与 `end` 之间的音频帧，区间外忽略。**

8. **双方必须忽略未知字段与未知枚举值。**
   这条是「`caps` 只增、非破坏改动不抬 `proto`」（§6）得以成立的**地基**——
   没有它，每次加字段都会让严格校验的实现拒绝整条消息，于是被迫抬 `proto`，
   `proto` "只在破坏性改动时递增"的语义随之失效，§6 整节论证作废。

   未知枚举值的 **fail-safe 方向**（宁可保守，不可乱来）：

   | 遇到未知 | 处理 | 为什么 |
   |---|---|---|
   | 未知字段 | 忽略 | — |
   | 未知 `reason` | **不送转写** | 把错误文字注入输入框，比丢一次转写严重得多（§8.2 设立 `reason` 的动机） |
   | 未知 `code` | 按 `retryable` 决定行为，文案走通用兜底 | `retryable` 已提供语义，客户端**不需要认识 `code`** |
   | 未知 `state` | 视为未知，不做 UI 门控 | — |

   > 💡 `retryable` 在这里兑现了它的价值：它不只是给人看的，
   > 它让**未知错误码也能被正确处理** —— 这正是 §9.2 说它"比 `code` 更重要"的原因。

## 13. 背压与服务质量

### local-mic 的义务

- **每客户端一个独立的、有界的发送队列 + 专用写线程**
- **该队列必须是单一 FIFO** —— 音频帧与 JSON 事件帧**同队**（硬要求，理由见下）
- 队列上限建议约 **1 秒音频**
- 溢出时**丢弃最旧的音频帧**；**事件帧（JSON）不得丢弃**
  （JSON 每次才几十字节，丢了会让客户端语义错乱，成本完全不对等）
- **不得阻塞采集线程**（音频约 15 ms 一帧，采集线程一旦被卡，后果是丢帧甚至掉线）

### 为什么必须这样（故障链，已完成取证）

```
客户端卡住 / 在调试器里断点 → 不读 socket
        ↓
本地 socket 发送缓冲满
        ↓
阻塞式写（且持着该连接的写锁）→ 卡住
        ↓
调用线程 = 采集线程被卡住
        ↓
15 ms 一帧的音频开始堆积 → 缓冲溢出
        ↓
丢帧，或整条设备连接断开
```

而且广播是**逐客户端依次发送**的，所以**一个卡住的客户端会挡住它后面所有客户端** ——
慢客户端的影响不是局部的。

触发场景不需要很极端：**在客户端里打个断点调一下就会撞上**，是开发期必然遇到的。
降级方式也必须是正确的：**丢音频帧像丢包（可接受），阻塞则像断线（不可接受）。**

### ⚠ 为什么必须是单一 FIFO

若实现成"音频队 + 事件队"两个队列，溢出丢音频帧时，`end` 会越过还在排队的末尾音频帧先到达
⇒ 违反**不变量 2**（"`end` 之后不再出现属于本段的音频"）
⇒ 客户端收到 `end` 即封段，随后到达的末尾音频帧被判为"区间外"而忽略
⇒ **每句话结尾丢半个字**，且极难归因。

这正是 §12.2 那个 30 ms 收尾窗口要防的事 —— 别在队列层把它破坏掉。

### 一条实现要求

音频帧的**构造动作要放在订阅者过滤之后**。
先构造整帧再遍历发送的话，无人订阅时就是每 15 ms 白构造一帧 ——
PCM16 下这是 **32 KB/s 的无用功**。
（仅靠"客户端数为 0 就返回"不够，因为可能存在"连着但不订阅音频"的客户端。）

### 客户端的义务

- 及时读取 socket，不长时间阻塞
- **不得假设音频完整**：可能丢帧（丢帧表现为音频有缝隙，属已声明的降级行为）

## 14. 一致性夹具（防止文档与实现脱钩）

协议层复用项目**已经验证过**的机制：ADPCM 的两份实现靠共享黄金向量锁死，
local-mic 的 `--selftest` 比对 12/12 逐字节一致。协议层照抄这个模式。

### 14.1 夹具文件

`conformance/protocol-vectors.txt` —— 消息级夹具，**单一数据源**，
由 C# 侧（local-mic）与 TS 侧（诊断页 / 插件）各跑一遍同一个契约测试。

夹具条目形如：

```
# 方向 输入 → 期望
L→C  {"op":"ready","proto":1,...}                    => 接受
L→C  {"op":"ready"}                                  => 拒绝：缺 proto(=0)
C→L  {"op":"hello","proto":2}                        => 拒绝：proto_mismatch
C→L  {"op":"hello"}                                  => 拒绝：缺 proto(=0)
C→L  {"op":"write","data":[12,0]}                    => 拒绝：op_not_supported（保持连接）
C→L  {"op":"future_op"}                              => 忽略 + 告警（真未知 op）
L→C  hex:02 <480 bytes>                              => 480 字节 = 240 个 s16le 样本
L→C  hex:02 <481 bytes>                              => 拒绝：长度非偶数
L→C  hex:01 <n bytes>                                => 忽略 + 告警（proto 1 未定义）
L→C  {"op":"capture","phase":"end"}                  => 拒绝：end 必须带 reason
L→C  {"op":"ready","proto":1,...,"future_field":1}   => 接受：未知字段忽略
L→C  {"op":"device",...,"fw_version":"2671"}         => 接受：未知字段忽略
L→C  {"op":"capture","phase":"end","reason":"vad"}   => 接受：未知 reason ⇒ 不送转写
```

**必须包含的负例**（正例测不出漂移）：

- 缺 `proto` 的 `hello` / `ready` ⇒ 必须被拒
- `proto` 不匹配 ⇒ 必须明确报错，不得"警告后继续"
- 出现 `uuids` 字段 ⇒ 测试应**断言它不存在**（防止硬件词汇回流）
- `phase:"end"` 缺 `reason`
- 奇数长度的 `0x02` 载荷
- `C→L` 的 `write` / 任何设备命令 ⇒ 必须回 `error{code:"op_not_supported"}` 并**保持连接**，
  且**不得产生任何设备写入**（§4.2）。注意它不是"未知 op"，是**已知但被删除的 op**

**必须包含的正例**（正例与负例缺一不可）：

- `hello` / `ready` / `device` 带**未知字段** ⇒ 必须接受并忽略
- `end` 带**未知 `reason`** ⇒ 必须接受，且**不送转写**
- `error` 带**未知 `code`** ⇒ 必须按 `retryable` 处理，不得拒绝

> ⚠ **为什么正例和负例都要有**：只写负例会自然催生"未知即拒"的实现，
> 而那会堵死 §6 的 `caps` 只增路线 —— 每次加字段都被迫抬 `proto`。
> 负例防漂移，正例防僵化，两边夹住才成立（不变量 8）。

### 14.2 为什么必须有夹具，而不是靠文档或代码

**证据就是这份文档的诞生过程。** 在整理规范时，一次凭记忆的接口复述
判定"某个字段代码没发"（依据是该构造函数只有 3 个参数），
而实测该字段**确实被发出**（参数个数与输出字段个数不等价）。

误判的原因不是没读代码 —— **读代码的人也会记错**。
所以真源不能是任何人的记忆，也不能是散文，

**必须是可执行的**：`--selftest` 的退出码，比任何一段文档都可靠。

| 事项 | 为什么不做 |

| `codec` 逃生舱字段 | 接缝唯一编码已定为 `s16le`。提前设计只是多一处能漂的地方；将来真需要再加可选字段 |
| 流式/分段语义 | 接缝给的 PCM16 是连续样本，消费侧按自己的采样数切片即可，**协议不需要配合** |
| 重采样 | 真正的 DSP（抗混叠/多相滤波），net48 手写是工作量 + 音质风险。v1 不做，格式不符就显式报错 |

| 独占主控 / 租约 | 需心跳 + 接管机制，失败模式（主控僵死、无人接管）极难排查。改用订阅语义 |
