## 1. 硬件：RC003-MS

| 项 | 值 |
|---|---|
| 全称 | 小米蓝牙遥控器 2 Pro |
| 型号 | **RC003-MS**（⚠️ 见下方修正） |
| 蓝牙 | **5.4** |
| 电池 | 300 mAh，USB-C 充电（非干电池） |
| 麦克风 | 内置 |

| 价格 | ¥99 |
| 尺寸/重量 | 138 × 35 × 8.9 mm / 61 g |

### ⚠️ 实测修正：DIS 报的型号是 `RC003`，不是 `RC003-MS`

连上后读标准 **Device Information Service (0x180A)** 的实测值：

| 特征 | 实测值 |
|---|---|
| `2A24` Model Number | **`RC003`**（**无 `-MS` 后缀**） |
| `2A29` Manufacturer | `MIOM` |
| `2A27` Hardware Revision | `V2.0` |
| `2A26` Firmware Revision | `2671` |
| `2A25` Serial Number | `250519` |
| `2A00` Device Name（`0x1800`） | `小米蓝牙语音遥控器\0`（**末尾带 `\0`，需 Trim**） |

**⇒ 型号识别必须按前缀匹配**（`DeviceProfiles.cs`）。写死 `== "RC003-MS"` 会永远匹配不上，
然后**静默退化成未知设备**——这类 bug 极难发现。

**未知型号不被拒绝**：ATVV 是 Google 的通用协议，别家遥控器可能完全可用；界面显示「型号 · 未验证」并注明，由用户判断。加新设备只需在 `DeviceProfiles.Known` 加一行。

### 电量（`0x180F` / `2A19`）

实测属性为 **Read + Notify**（读数 99%）：

- 连接后先读一次
- 订阅 notify 后由遥控器主动推送，**不需要轮询**（轮询会打扰一个省电设备）
- **断线后保留上次读数但灰显**，不让过期数字看起来像实时值

另外有两个未知服务：`8a7a0001-…`（3 组 N/W 特征）与 `000001bf-…`（Vendor specific），用途不明，暂不动。

> 那颗**可自定义 TV 键**是白捡的第 8 个输入源，v2 可考虑利用。

### 🔴 连接行为：断连约 1 分钟后休眠，必须按键唤醒（2026-10-04 真机）

这是**设备侧**的电源管理行为，与 ATVV 协议无关，但直接决定 local-mic 的重连策略该怎么写。

| 场景 | 实测结果 |
|---|---|
| **静置**（不碰它） | **34 分钟零断链** ⇒ 正常放着不会自己掉线 |
| 断连 **≤35 s** 后恢复链路 | **≤6 s 自己连上** —— 还没睡 |
| 断连 **≈76 s** 后恢复链路 | 🟡 **干等 18 轮 / 210 s 后自己连上**（**唯一自愈实例，n=1**；notes 判为 Windows 自动回连触发） |
| 断连 **≈2 min** 后恢复链路 | **干等 3–5 分钟、22–30 轮重试全部失败**；**按一下任意键 ⇒ 1–5 s 内连上** |
| **拿远出范围 ≈55 s** 后拿回（2026-10-06 T6） | **链路 1 s 内自愈**（Reconnecting 第 5 轮接通）——但拿回瞬间枚举抖动踩中误判，见下方 ⚠ |

> ⚠ **"必须按键唤醒"要按上面的数据读精确**：按键不是**唯一**解，是**快得多的解**
> （1–5 s vs 干等 210 s）。2026-10-05 复核时发现上面那一行自愈样本曾被漏记 ——
> 漏它的后果是让人以为"不按键就永远回不来"，进而把 `Unresponsive` 实现成停止重试，
> 那就把用户不在电脑旁时唯一的恢复路径掐掉了。状态侧的表述见 `docs/STATE-MODEL.md` §2.4–2.5。

**两轮独立对照（X7 / X8）结果一致**，不是单次巧合：

```
断连 2 min → 开蓝牙 → 干等 3 min 44 s（22 轮）全败 → 按方向键 → 5 s 内连上
断连 2 min → 开蓝牙 → 干等 5 min 04 s（30 轮）全败 → 按方向键 → 1 s 内连上
```

> ⚠ **恢复瞬间的枚举抖动会踩出假 `pairing_required`（2026-10-06 T6 实测，致命）**：
> 拿回后链路 1 s 就连上，但紧接着 `枚举服务失败：Unreachable`（被 `BleRemote.cs:329`
> 标成 `connect_timeout`，码不对但 retryable=true，行为正确），重试后再连上又报
> `枚举特征失败：AccessDenied` → 同处 `auth=(status==AccessDenied)` 直接判
> **`pairing_required` + `retryable=false` ⇒ 重连循环停止**。设备明明已配对
> （前一秒的 device 行还显示"配对 是"）、人就在旁边，helper 却宣告配对丢失、永不再试。
> 这正是 `docs/STATE-MODEL.md` §6 已定改造（判配对改查注册表，不看 WinRT 状态）要消灭的；
> 实测证明 `AccessDenied` 不只在"重配对后首连"（PITFALLS #32）出现，**普通抖动恢复也会**。
>
> ⚠ **恢复后的 `AccessDenied` 不是瞬时竞态，会持续 36–54 秒（2026-10-06 锡箔纸屏蔽 ×2 实测）**：
> 锡箔纸包遥控器 30 s（= 拿远模拟，断链秒级可检）→ 拆开 → **链路秒级回连**
> （`ConnectionStatus=Connected`），但随后每轮重连（每轮都是**新建** device 对象，
> 排除本机缓存）都在 `枚举特征：AccessDenied` 上失败，连撞 **10 / 13 轮（36 s / 54 s）**
> 才放行成功。最可能是**遥控器侧的 ATT 会话还绑在旧链路上**，要等外设自己的链路丢失
> 超时（30–60 s 量级）才接受新 GATT 操作。含义：① `pairing_required` 绝不能由
> `AccessDenied` 推出（这期间 `reg=yes`/`IsPaired=True` 全程在场）；② 这段"链路通但
> GATT 未就绪"与"链路不通（wait=timeout）"是**可区分的两种签名**，判定层应分态；
> ③ 它同时是 `BleRemote` 失败不 `DisposeDevice` 导致脑死亡的实锤现场 —— 修复后
> 两轮 23 次失败全部扛住并自愈。

> ⚠ **睡死的设备，光撤掉障碍是叫不醒的（2026-10-06 场景 3，锡箔纸催眠法实测）**：
> 锡箔纸包 5 分钟（断连 >2 min ⇒ 已睡死）→ 拆开 → **重连轮次照样全部 `wait=timeout`，
> 持续 3 分多钟无任何恢复迹象**（n=47..68）；**按一下方向键 ⇒ 链路 1 s 内由遥控器侧主动回连，
> 约 2–4 s 全部就绪，且这次恢复完全没有 AccessDenied 阶段**。对照：同场较早一次只包 2.5 min
> （还没睡死）就拆，链路秒回、AccessDenied 只持续约 5 s。两个可归因的相关性（各 n=1–2，
> 别当定律）：**遥控器主动发起的回连**（按键唤醒后）⇒ 无/极短 AccessDenied；
> **Windows 侧自动回连**（屏蔽刚撤、外设还没察觉旧链路已死）⇒ 36–54 s AccessDenied。
> 含义：`Unresponsive` 的指引"拿近点 + 按一下"里，**"按一下"才是必要条件**——
> 睡死状态下把遥控器拿到嘴边也没用。

> ⚠ **`BLE_Unpaired` 签名（2026-10-06 场景 5，Windows 设置里删除设备实测）**：
> 删除配对的瞬间**活链路立刻被掐**（`ConnectionStatusChanged→Disconnected` 秒级）；
> 之后每轮重连的签名是 **`reg=no` + `IsPaired=False`**（删除后 ≤13 s 内两者都翻，
> 首个采样点已翻，大概率即时），但 `FromBluetoothAddressAsync` **照样建得出对象**
> （13–19 ms，名称还能解析出 "MI RC"，走的本机缓存），`status=Disconnected`，
> 10 s `wait=timeout`。**判 `BLE_Unpaired` 不能用"建不出对象"，必须看注册表 `reg`；`IsPaired` 仅保留作取证字段，不参与判定**。
> 重配过程：设备在 Windows「添加设备」列表里**不广播、找不到**，按一下遥控器方向键
> 立刻出现；配对完成 ⇒ 链路秒回、首个完整 GATT 打开直接成功——**PITFALLS #32
> （重配后首连 AccessDenied）本次未复现**，不是必然行为。⚠ 注册表键在重配完成后
> **仍有数秒滞后**（配对已提交、link 已 Connected，下一轮 reg 仍采到 `no`）——
> 用 reg 判 `BLE_Unpaired` 时"刚配对完"的窗口期要容错（此时 link 本来就通，不是问题）。

**对实现的三条约束**：

1. ⛔ **别靠"更快/更多次重试"解决断连恢复** —— 设备休眠时**根本不响应**，
   连"主动踢一脚"（多发一次 `GetGattServicesAsync`）也没用。
2. ✅ **正解是告诉用户按一下遥控器** —— 且必须**条件触发**（断连且重试若干轮失败后才提示）。
   常驻提示是错的：静置不掉线，99% 的时间它都是噪音。
3. ⚠ **休眠阈值的精确秒数未量化 ⇒ 不得写进代码**（那是对固件行为的硬编码假设）。
   已知区间（2026-10-06 场景 3 收窄）：断连 2.5 min 还没睡、断连 5 min 已睡死 ⇒
   阈值在 **2.5–5 min** 之间（用户经验值"断连后约 2 min"与本数据相容）。
   **连接保持期间不睡**（34 min 零断链；用户经验：连上后几小时不掉）。文案表述为
   「若长时间连不上，请按一下遥控器」，**不要写「等 X 秒后按键」**。

**已排除**：关蓝牙时**不存在"假连接"** —— 三次复现，`ConnectionStatusChanged`
都在同一秒触发 `disconnected`，断链事件是可靠的。

**仍未验证**：休眠期间遥控器**是否还在广播**。唯一一次扫描因时机错误不作数
（扫的时候链路其实已恢复）。要验须在**断链期间**连续 scan。

## 2. ATVV 协议规格（可直接写代码）

协议已被他人完整逆向，规格带单元测试。**不要自己逆向。**

### 2.1 GATT UUID

```
Service base: AB5E0000-5A21-4F05-BC7D-AF01F617B664
  0001 = Service
  0002 = TRANSMIT（主机 → 设备）
  0003 = AUDIO（设备 → 主机，音频数据）
  0004 = CONTROL（设备 → 主机，控制事件）
```

### 2.2 主机 → 设备（写 TRANSMIT）

| 命令 | 字节 |
|---|---|
| GetCaps | `0A 01 00 00 03 03` |
| MicOpen | `0C 00`（协议版本 ≥ 0x0100）/ `0C 00 <codec>`（旧版） |
| MicClose | `0D <session_id>` |
| **MicExtend** | `0E <session_id>` |

### 2.3 设备 → 主机（CONTROL 通知，首字节 = opcode）

| opcode | 含义 |
|---|---|
| `0x0B` | Caps（能力） |
| `0x08` | MicOpenRequested |
| `0x04` | StreamStarted |
| `0x00` | StreamStopped |
| `0x0A` | DecoderSync（predictor i16 BE @[4..6]，step_index @[6]） |

### 2.4 Capabilities 解析

- 判定设备可用：`sample_rate == 16000`（即 `codecs & 0x02`）
- **RC003 固件怪癖（实测复现）**：`version` 报 `0x0100`，而 `codecs` 字节**时 0 时 2**

  | 实拍响应 | 说明 |
  |---|---|
  | `0b 01 00 02 03 00 78 00 00` | codecs = `0x02`（正常） |
  | `codecs = 0` 的形态 | codec 信息藏在 `[4]` 的低两位 |

  ⇒ `Atvv.ParseCaps()` 里那个回落分支（`codecs=0` 且 `version>=0x0100` 时取 `b[4]&0x03`）**别当冗余代码删掉**。

### 2.5 音频

| 参数 | 值 |
|---|---|
| 采样率 | 16 kHz |
| 声道 | 单声道 |
| 编码 | **IMA ADPCM 4 bit** |
| 帧大小 | **120 字节/帧**（按 caps.frame_size 走，别硬编码） |
| nibble 顺序 | **高 4 bit 先** |
| 解码状态 | **帧间连续**（保留 predictor / step_index 作为下帧初始状态） |
| 每帧时长 | **15 ms**（120B = 240 samples ÷ 16 kHz） |

**这个公式用来验证链路质量**：`到达帧数 × 15 ms ÷ 按住时长 = 实时送达率`。

> ⭐ **ATVV 解码输出（16 kHz 单声道 PCM16）与 dsh 语音链路要求的 WAV 格式完全一致，中间零转换。**

**别用 wall-clock 收集窗口当分母**：拿 10 秒窗口除 3.42 秒的音频会算出 2709 B/s 并误报"吞吐不足"，真实值是 8000 B/s。

### 2.6 状态机容错（固件怪癖全录）

1. **MTU 问题在 WinRT 侧不存在** ✅（已实测，原"必须协商到 247"的担忧不适用）
   按住 3.42 秒收到 **228 帧，全部 120 字节，无一截断，零丢帧** ⇒ 实际吞吐 **8000 B/s，正好是理论值**。
2. **固件会跳过 `0x08` 直接发 `0x04`**。状态机不能把 MicOpenRequested 当必需中间态，否则卡死。
3. **Stop 事件会重复**，必须去重（用 session_id + 当前状态联合判断），否则乒乓。
4. **⚠️ 固件免费音频窗口只有约 5.7 秒**（不是 60 秒！）。超过就被精确掐断。必须每 **2.5 秒**发一次 `0x0E <session_id>` 续期：StreamStarted 时排期，StreamStopped 时取消；协议版本 < 0x0100 编码失败则不排期。
   > 用户说 prompt 一句话轻松超 5.7 秒，**这个坑必然踩到**。流传的"60 秒上限"是错的。
5. **⚠️ 连接初期会收到遗留通知**（实测刚连上就收到 `04 03 02 11`）。不丢弃就会在用户还没按键时误判成"已按下"并发 MicOpen。
   **解法：自检开始前先静默 800 ms**，或用 `armed` 标志把关。（Python 版踩过，C# 版已修）
6. **🔴 `0x00 StreamStopped` 会迟到**（真机 2026-09-29 实测）。松手后它不按时到，往往要等**下一次按键**
   才随连接激活一起投递 —— BLE 空闲时连接间隔变大，通知要等下一个连接事件。
   症状：**松手后采集窗口不关，转写永远不出结果；再按一下才把上一段吐出来。**
   **解法：音频静默看门狗**——`0x00` 与"音频停够 600 ms"两者谁先到谁生效（`AtvvSession.SilenceTimeoutMs`）。
   600 ms 的依据：ATVV 每 15 ms 一帧，正常流里不可能出现连续 40 帧空档；而人对"松手到出字"的容忍在 1 秒内。
   看门狗只在**收到首帧之后**才启动，这样"开麦后零音频"仍归 `timeout` 判，两条超时各管一件事。
   迟到的 `0x00` 到达时窗口已关，被 `!_capturing` 挡掉，不会二次结束。
   > 只等 `0x00` 是**错的**，任何一侧都别这么写。UI 自检（LocalMic.RunSelfTestAsync）与会话机都有这条兜底。
7. **🔴 「抢跑」那一按会毁掉这次录音**（真机 2026-09-29，两份日志 `debug/20260929-230551`、
   `20260929-232257` 共同定因；**本条已按第二份日志修正过，别采信更早的说法**）。
   自检从点击到提示「请按住」要 1–2 秒（连接 + 800 ms 静默 + GetCaps），**这期间的按下会被丢弃**
   （`armed` 未置位）。用户在这段"连接遥控器"状态里就按住说话 ⇒
   设备照样开流（约 2–3.7 秒）并自己收尾，而 local-mic 全程没在采集。
   现象：界面显示"已录制 2 秒"却不是用户说的话，或干脆毫无反应。
   > ⚠ 早期曾把它误判为"设备自己跑遗留流"。两份日志拼起来看，那 2 秒音频**就是用户抢跑按出来的**，
   > 设备不会凭空开流。结论修正后，下面的防线仍然成立（抢跑的流确实会污染下一次录制），
   > 但"设备会自发开流"是错的，别照它设计。
   它带来两个后果，两侧都要防：
   - **按下前到达的 `0x00` 会把等待提前打断**。自检里若让遗留 `0x00` 置位 `stopTcs`，
     用户真正按下后 `WhenAny(stopTcs)` 立即返回 ⇒ 录制在按下后 25 ms 就被收尾。
     症状：UI 显示"已录制 2 秒"，播出来却是遗留流，**用户说的话只进 2 帧**。
     修法：`0x00` **只在按下之后才生效**，之前的一律丢弃。
   - **按下前的音频不得计入本次录音**，否则统计被整段污染。
   - **抢跑必须有反馈**：未就绪时收到 `0x04`/`0x08` ⇒ 提示「按早了，请等提示出现再按」。
     静默丢弃会让用户以为程序坏了（真机上正是这么误会的）。UI 初始提示也从「请按住」
     改成「正在准备…」，别催着用户抢跑。
   > 生产路径（会话机常驻、Arm 一次后一直就绪）不受影响 —— 真机已验证 start→音频→end 完整走通。
8. **🔴 设备要收到 `MicOpen` 才真正送流**（真机取证同上）。真实时序是：
   ```
   用户按下 → 设备发 0x04 → 主机回 0x0C MicOpen → 设备再发一个 0x04 → 音频才来
   ```
   固件跳过了 `0x08`，于是**第一个 `0x04` 兼有"请求开麦"的含义**。
   ⇒ 会话机只在 `0x08` 分支回 MicOpen 是不够的：插件上线后按下去不会有声音，只能等 timeout。
   修法：**开麦后 300 ms 仍无音频 ⇒ 补发一次 `0x0C`**（`AtvvSession.MicOpenNudgeMs`）；
   已发过或已有音频就不补，避免打断正在跑的流。
   `_micOpenSent` 只在一段**结束**时清零，不在 `0x04` 到来时清零 ——
   否则 `0x08 → 回 MicOpen → 0x04` 这条标准流程会被误补第二次。

## 3. Windows BLE / WinRT 通道（local-mic 走的就是它）

| 事实 | 结论 |
|---|---|
| `Windows.Devices.Bluetooth` 是 **DualApiPartitioned** | 微软官方确认**桌面应用可直接调用**，无需打包成 UWP |
| net48 需 NuGet `Microsoft.Windows.SDK.Contracts` | 仅构建期引用，不进产物 |
| **未打包桌面应用的 capability 声明非强制，但涉及「配对」时风险高** | ⇒ local-mic **不主动触发配对**，只按地址直连已配对设备 |
| 0x180A / 0x180F 在 Web Bluetooth 黑名单里 | **WinRT 本地不受该限制**（黑名单已无意义） |

设备地址从注册表读：`HKLM\SYSTEM\CurrentControlSet\Enum\BTHLE\Dev_xxxxxxxxxxxx`，字节序**不需要反转**。
本机遥控器实测：`Dev_c05d39f850c7` → **`C0:5D:39:F8:50:C7`**。

> **配对交给 Windows 自己**（用户明确要求）：local-mic 不调 `PairAsync`，只**检测配对状态**并直连；"在 Windows 中配对遥控器…"菜单项打开 `ms-settings:bluetooth`。

### 3.1 🔴 怎么启动 local-mic：进程完整性级别决定一切

Windows 的**强制完整性标签**带 `No-Write-Up` —— **低完整性（Low IL）进程不能写高完整性对象**。而进程 IL 不是天生的：

```
进程 IL = min(启动者 IL, exe 文件的强制完整性标签)     ← 两个因子，任一低结果就是 Low
```

Low IL 下 Windows **硬性拒绝** `Shell_NotifyIcon`（`GetLastError=5`，PITFALLS #22），症状是"双击了、什么也没有"。

| 启动方式 | 启动者 IL | 结果 |
|---|---|---|
| 资源管理器 / 普通桌面双击 | Medium | ✅ 托盘图标正常 |
| **Low 完整性上下文**（AI 编码助手的沙箱终端、部分加固/沙箱软件、低权限计划任务） | Low | ❌ **没有托盘图标**，自动弹出主窗口 |

仓库目录已用 `icacls /setintegritylevel (OI)(CI)M` 设为 **Medium**（PITFALLS #26）—— 但那只修好了公式的**第二项**。**启动者**那一项低时照样出不来图标（PITFALLS #31）。

同一个 Low 还有第二个后果：**Low 进程写不进这个 Medium 仓库**（标签上的 `(NW)` = No-Write-Up），于是 Low 上下文里的构建一律报 `error MSB3491: Access denied`。⚠ **这个报错与 DACL 无关**——`icacls` 显示本账号完全控制俱全，拒绝来自完整性级别（PITFALLS #30）。⛔ 别用 `icacls /setintegritylevel … L` 去"消掉"它：那正是 #26 修掉的 Low 标签，降回去托盘图标立刻复发。

**判自己在哪条路径上：**

- 主窗口标题带 `（完整性 Low：系统不发放托盘图标，关窗即退出）` ⇒ 走了兜底，**没有托盘图标**
- 标题干净 + 通知区（可见区，非 `^` 折叠区）有色块图标 ⇒ 正常路径
- `whoami /groups` 看自己的 `Mandatory Label`（Low = `S-1-16-4096`）；`icacls <路径>` 看对象标签

**⇒ 从桌面/资源管理器双击启动 local-mic，不要从 AI 助手的沙箱终端或低权限计划任务启动。**

> 读法参考：兜底本身是设计内的正常行为（`Integrity.TrayIconUnavailable` → `TrayApp.RunWithoutTray`，直接把主窗口开出来并把"关窗"改成"退出"，避免变成无图标无窗口的隐形进程）。Win11 上想确认托盘图标到底注册上没有，用 UI Automation 遍历 `Shell_TrayWnd` —— 经典的 `TB_BUTTONCOUNT` 在 24H2 已经失效（通知区域是 XAML 的）。

## 4. 键位真值表（RC003 在 Windows 上）

> **v1 不使用本节任何内容**——PTT 走 ATVV 的 CONTROL 事件（AGENTS.md 定案 A7）。本节是 **v2 做审批控制时的输入源清单**。

### 4.1 可用

| 按键 | usage / VK | 说明 |
|---|---|---|
| **语音键** | F5 (`0x74`) | ✅ **驱动 ATVV 会话**（v1 不需要这个 VK，直接用 CONTROL 事件） |
| 确认 | `0x0028` → VK_RETURN | ✅ |
| 主页 | `0x004A` → VK_HOME | ⚠️ 会连带影响实体键盘 Home |
| 方向键 ×4 | 标准方向键 | ✅ |
| 电源键 | `vk=0xFF / scan=0x5E` | ✅ **唯一存活的非标键**，不与实体键盘冲突 |

> 本节实测于**原生 Windows 应用**环境。**若 v2 要在浏览器里用这些键，必须重测**——浏览器能收到一些原生应用拿不到的键（例如 Chrome 会派发 `BrowserBack` / `AudioVolumeUp` 这类 `KeyboardEvent.key`），结论可能不同。**不要直接照搬本节的"不可用"结论。**

### 4.1.1 🔴 语音键 = F5 ⇒ 在浏览器里就是「刷新页面」（真机 2026-09-30）

上表第一行已经写了语音键是 `F5 (0x74)`，但**没有人把它和"F5 = 刷新网页"连起来**。
后果由用户在真机上发现：切到**任意**网页按录音键，页面都会刷新。

```
按下语音键 ───► ATVV CONTROL 事件 ──► local-mic 开始采集   ✅ 我们要的
             └─► HID 键盘事件 F5 ──► 浏览器刷新页面  ──► 页面重载
                                                      └──► WebSocket 断开，录音中断  ❌
```

⚠ **"v1 不依赖这个 VK"不等于"不受它影响"**：PTT 走 CONTROL 事件没错，
但键盘事件照样发生，F5 照样刷新。**这是 v1 在浏览器里落地的第一道障碍，比协议问题更靠前。**

**已验证的缓解**（浏览器侧，免提权）：页面内 `keydown` 里只对**裸 F5**调 `preventDefault()`。
带修饰键的 `Ctrl+R` / `Ctrl+F5` / `Shift+F5` 放行给用户刷新；诊断页的「屏蔽刷新键」开关即此实现，默认开。
写 dsh 插件时必须带上裸 F5 拦截，否则遥控器语音键会刷新页面。

另两条待评估，别急着上：Windows `Scancode Map`（全局重映射，会波及实体键盘）、
驱动层按设备过滤 HID（复杂，需提权）。

> 副作用之外的好消息：**既然音频走 local-mic 的 WebSocket，浏览器就不需要任何特殊能力** ——
> Firefox / Safari 一样可用。

### 4.2 不可用（Windows 侧零事件）

| 按键 | usage |
|---|---|
| 返回 | `0x00F1` |
| 音量 + | `0x0080` |
| 音量 − | `0x0081` |

### 4.3 三键失效的根因（已实测闭合，不要重复排查）

```
设备确实上报（HidP_GetButtonCaps 取证：三个 usage 确实在报告里）
    ↓  报告到达 WUDFHost.exe（提权只读实测，30 次命中）
    ↓
Windows 事件层零事件（Raw Input 对照组有效）
    ⇒ 丢弃发生在 HID→VK 键码映射阶段（kbdhid）
```

**不是设备不上报，是 Windows 的 HID→VK 映射表里没有这三个 usage。**

**免提权的四条路已全部实测 failed**（别再试）：

| 通道 | 结果 |
|---|---|
| 用户态 `CreateFile(GENERIC_READ)` 直读 TLC | `err=5` |
| 厂商 GATT `8A7A0001` 的 3 个通知特征 | 可订阅但零通知 |
| GATT HID `0x1812` 特征枚举 | 全部 AccessDenied |
| Raw Input 注册 5 种组合 | 三键零事件（对照组精确到达，自证有效） |

**唯一可行解**（v2，v1 不要做）：提权注入 `WUDFHost.exe`，拦截 `DeviceIoControl` / `IOCTL 0x80018483`，在 `onEnter` 改写 usage（必须在 onEnter，实测 onLeave 输出变化 0/30）。需一次 UAC，**不装内核驱动、不开 TESTSIGNING、不关 Secure Boot、不重启**。

### 4.4 能不能"只改遥控器的键、不动实体键盘"？—— 能动，但禁区很清楚

**先回答最容易踩的那条**：

> ❌ **改 Windows 的 `Scancode Map` 一定会误伤实体键盘。**
> （`HKLM\SYSTEM\CurrentControlSet\Control\Keyboard Layout`）
> 它按**扫描码**映射，而扫描码里**不含设备身份** ⇒ 规则对所有键盘生效。
> 改 F5 就是改掉了**每一把**键盘的 F5。另需管理员权限 + 重启。
> **同一条道理对低级钩子（`WH_KEYBOARD_LL`）也成立** —— 钩子回调拿不到设备 ID。

**参考项目（`getsayall/remote-mic-app-windows`，Rust）怎么做的：不走系统映射，走"吞键 + 归因"。**

| 层 | 职责 | 关键限制 |
|---|---|---|
| **Raw Input**（`RIDEV_INPUTSINK`） | 归因：`WM_INPUT` 的 `hDevice` 能认出"这是遥控器" | **只能观察，不能拦截** |
| **LL 钩子** | 执行：吞掉该键 | **没有设备信息**，只能靠"武装"猜 |

两者配合的三条归因策略（`crates/sayall-windows/src/key_gate.rs` 原文归纳）：

1. **直接归因族** —— 物理键盘绝不会产生的键（`VK 0xFF` 族：返回/电源/音量）⇒ 直接吞，无需归因
2. **常驻抑制族** —— Home / TV 这类：**遥控器在线期间一律吞**。代价是实体键盘的 Home 被接管，
   项目记录里"用户确认接受"，断开连接即恢复
3. **武装族** —— 方向 / Enter / **F5** 这类**两边都有**的键 ⇒ 必须先由 Raw Input 看到
   该设备的 HID 报文来"武装"，钩子在 60 ms 内有界等待后裁决

> ⚠ **它明确踩过我们这个坑**：早期用"全局 F5 钩子"，结果是
> "**不能再把桥接运行期间所有实体 F5 都被吞掉**"，因此改成源头拦截。
> 另：该项目的 `button_mapping.rs` 写着"**语音键不参与映射**…保持 ATVV 实时生命周期" ——
> 和我们 v1 的判断一致（PTT 走 CONTROL，不靠键盘）。

**对我们（语音键 = F5）的代价阶梯**：

| 方案 | 代价 | 够不够 |
|---|---|---|
| **页面内 `preventDefault`**（v1 已做，§4.1.1） | 只在本页生效，别处按语音键仍刷新 | ✅ v1 够用 |
| local-mic 加 LL 钩子 + Raw Input 归因 | **F5 属"武装族"**，而 RIT 先调钩子、后投 `WM_INPUT` ⇒ **孤立首按必泄漏**（第一次按还是会刷新） | ⚠ 对"按住说话"是致命的 |
| ↑ 改用"遥控器在线期间全局吞 F5" | 实体键盘 F5 在该期间失效（可用 Ctrl+F5） | 可行，但要用户拍板 |
| 设备源头替换（§4.3 的注入路线 / 内核过滤驱动） | 提权注入或驱动签名 | 唯一"零误伤"，成本最高 |

**结论**：v1 不要碰按键映射（PTT 本就不依赖键盘事件）。
真要"按设备改键"是 **v2 的审批控制**（方向键/确认键）才需要，届时按上表权衡。

> 顺带排除一条幻想：**改遥控器固件层的键位没有可行路径** —— ATVV 只承载音频，
> 厂商 GATT `8A7A0001` 的通知已实测零通知（§4.3），改键得靠官方 App，我们没有那条通道。

### 4.5 ❌ 已否决：把遥控器的 HID 键盘设备禁掉（2026-09-30 用户决策）

> **否决理由（用户原话）**：「不考虑这个方案，**其他按键也会用到**。」
> ⇒ 遥控器的方向键/确认键是 v2 审批控制的前提，禁用 HID 会把它们一起丢掉。
> **不要再提这个方案，也不要写进任何自动流程。** 以下留档，仅为将来若前提变化时可回查。

**思路**：既然 F5 是"遥控器被 Windows 当键盘"造成的，那就让它不当键盘。
比 §4.4 那套"吞键 + 归因"简单得多 —— 不需要钩子、不需要驱动、不需要提权注入。

**本机取证（2026-09-30）**：遥控器在这一层只对应**一个**设备实例：

```
HID\{00001812-0000-1000-8000-00805f9b34fb}_Dev_VID&012717_PID&32b8_REV&00a4_c05d39f850c7\9&106e0c67&0&0000
  ClassGUID   = {4d36e96b-e325-11ce-bfc1-08002be10318}   键盘类
  Service     = kbdhid                                    ← 键盘 HID 驱动
  DeviceDesc  = "HID Keyboard Device"
  ConfigFlags = 0                                         ← 启用中
```

（`0x1812` = HID over GATT 服务，`0x2717` = 小米 VID，`REV&00A4` 与参考项目记录的精确 HWID 一致；
它**只有一个顶层集合**，与 §4.3 的"RC003 只有一个键盘页 TLC"吻合 —— 所以禁用 = 所有实体键一起没。）

```powershell
# 停用（需管理员；完全可逆）
Disable-PnpDevice -InstanceId "HID\{00001812-0000-1000-8000-00805f9b34fb}_Dev_VID&012717_PID&32b8_REV&00a4_c05d39f850c7\9&106e0c67&0&0000" -Confirm:$false
# 恢复
Enable-PnpDevice  -InstanceId "HID\{00001812-0000-1000-8000-00805f9b34fb}_Dev_VID&012717_PID&32b8_REV&00a4_c05d39f850c7\9&106e0c67&0&0000" -Confirm:$false
```

| | |
|---|---|
| ✅ 好处 | F5 问题**从根上消失**（不产生键盘事件，无需任何拦截）；语音键照走 ATVV CONTROL |
| ❌ 代价 | **遥控器所有实体按键一起失效**（方向/确认/返回/音量/TV），只剩语音 |
| ⚠️ 未验证 | **禁掉 HID 后 local-mic 的 ATVV 连接是否还正常** —— 两者是同一 BLE 设备上的独立 GATT 服务，理论上互不影响，但**必须真机实测**，不许推断 |
| ⚠️ 其他 | 需管理员；重新配对后设备实例会变，可能要重新禁用；**必须在用户明确同意后才执行** |

**⚠️ 没有先例可抄，这条路要自己测**（2026-09-30 查证）：参考正主
`getsayall/remote-mic-app-windows` 的 `hardware/RC003/README.md` 全文**没有**
"禁用 HID / 让设备不再作为键盘"的尝试或结论 —— **它的方向恰恰相反**：
承认键盘身份，在 `kbdhid` 层次拦截并在报告层重映射（其 §5 结论：
"该设备在 Raw Input 里 100% 走键盘通道，HID 通道零报文"、"想按设备拦截，
过滤器要挂在 `kbdhid` 子节点"）。它只在"清场迁移"时提过一次
"设备管理器禁用再启用"，用途是释放被宿主占用的 Gadget DLL，与本方案无关。

> 唯一支持"可行"的**间接**证据是我们自己的实测：local-mic 在 HID 正常工作时
> **已经**能连上 ATVV（两者并存是既成事实）。但这不能推出"禁用 HID 后 ATVV 仍在" ——
> 禁用可能触发 BLE 链路重建，而 `mshidumdf` 往往是该连接的主要持有者。

> 它就是与 v2 冲突才被否决的（见本节开头）。**保留按键 ⇒ 语音键的 F5 副作用必然长期存在**，
> 于是浏览器场景下"页面内拦截"（§4.1.1）就是唯一手段；将来若要按键在 dsh 之外也生效，
> 只能回到 §4.4 的路线（吞键 + 归因，或 §4.3 的提权拦截）。
